# MCP Tool Gateway 改进方案

## 目标

- 修复当前参数过滤对复杂 JSON Schema 的误伤风险。
- 建立“调用前参数处理链”，把注入、裁剪、校验、告警从散落逻辑收敛到统一入口。
- 让工具选择与行为可预测（顺序稳定、冲突可控、日志可追踪）。
- 明确 hooks 是否值得引入，并给出可演进路线。

## 现状问题（基于现有代码）

- 参数过滤仅按 `properties` 白名单，可能错误忽略合法参数（`additionalProperties`/组合 schema）。
  - 位置：[mcp_tool_gateway.py](/Users/apple/Desktop/code/chat-agent/backend/app/mcp/mcp_tool_gateway.py)
- 工具名冲突仅 warning，`tools_map` 最终“后写覆盖”，调用目标不确定。
  - 位置：[mcp_tool_gateway.py](/Users/apple/Desktop/code/chat-agent/backend/app/mcp/mcp_tool_gateway.py)
- `get_tools_for_llm` 使用 `set` 导致输出顺序不稳定，影响模型工具选择一致性。
  - 位置：[mcp_tool_gateway.py](/Users/apple/Desktop/code/chat-agent/backend/app/mcp/mcp_tool_gateway.py)
- workspace 参数注入逻辑在执行器侧，与网关过滤链路分散。
  - 位置：[tool_executor.py](/Users/apple/Desktop/code/chat-agent/backend/app/agents/tool_executor.py)

## 方案设计

### 1) 参数过滤策略升级为“安全透传优先”

在 `MCPToolGateway` 中把 `_filter_tool_arguments` 改为规则化：

- 仅当 schema 明确 `type=object` 且 `additionalProperties is False` 且 `properties` 存在时，执行白名单过滤。
- 若 `additionalProperties=True/未声明`、或检测到 `oneOf/allOf/anyOf/$ref`，默认透传参数，不做误伤过滤。
- `removed_params` 统一排序，保证日志和提示稳定。

### 2) 建立调用前参数处理链（单入口）

在网关 `call_tool` 内增加轻量 pipeline（可先私有方法，不强制插件化）：

- `prepare_arguments`：调用前注入（如 `user_id/workspace_id`）、标准化。
- `filter_arguments`：按 schema 进行可选裁剪。
- `validate_arguments`：最小校验（至少 required 缺失检测；可选接入 `jsonschema` 完整校验）。
- `collect_warnings`：沉淀为统一 warning 结构，交给上游 `ToolExecutor` 拼接用户可读提示。

### 3) 工具索引与顺序稳定化

- `rebuild_tool_index` 增加冲突策略开关：
  - 默认 `strict=False`：保留兼容但记录结构化冲突信息。
  - 生产推荐 `strict=True`：遇冲突抛错并阻止启动（fail-fast）。
- `get_tools_for_llm` 不再用 `set` 直接迭代，改为“按 registry 顺序 + 去重后保序”。

### 4) 可观察性与配置化

- `call_tool` 超时从固定值改为配置项（全局默认 + server 级覆盖）。
- 新增结构化日志字段：`schema_mode`、`removed_params_count`、`validation_failed`、`conflict_policy`。
- `health_check` 文案与语义分离：区分 `registered` 与 `available`。

## hooks 方案建议（结论）

不建议第一阶段就上“通用 hooks 框架”。

推荐分两步：

1. **第一阶段（现在）**：在 `MCPToolGateway.call_tool` 内实现内聚的固定 pipeline（最小改动、强约束、易回归）。
2. **第二阶段（需要扩展时）**：当出现 >=3 类独立横切需求（审计脱敏、配额限流、多租户策略、A/B 路由）再抽象为 hooks（如 `before_call/after_call/on_error`）。

原因：

- 当前注入与过滤场景集中，过早 hooks 会增加执行路径复杂度与调试成本。
- 固定 pipeline 已能满足“参数忽略 + 调用前传值”的核心诉求。
- 后续从 pipeline 平滑演进为 hooks 成本低（方法签名可提前对齐 hook 形态）。

## 验证计划

- 单测：
  - `additionalProperties=True` 时不误删参数。
  - `additionalProperties=False` 且 properties 存在时正确过滤。
  - required 缺失时在调用前报错。
  - 工具冲突在 strict 模式下失败、非 strict 模式下可观测。
  - `get_tools_for_llm` 顺序稳定。
- 回归：
  - `agent-skills-mcp` 的 `user_id/workspace_id` 注入链路可用。
  - 现有 filtered warning 仍能正确反馈到模型上下文。
