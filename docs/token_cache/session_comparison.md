## 3. 关键发现

### 3.1 token 级缓存率持平 (82.7% → 84.5%)

两个 session 的整体 token 级缓存率非常接近。这说明：
- **优化前的 session 本身已经是「好的 case」**（prod 环境 system prompt 热缓存 + 用户测试问题相对固定）
- 优化的收益主要体现在**消除退化 case**（如之前分析的 Trace C 从 7.5% → 45.4%），而非提升已经良好的 case

### 3.2 低命中区间消除

优化前有 1 个 generation 在 0-20% 区间（a5c16632 的 iter1，cache% = 2.6%，input 高达 228,727），优化后该区间降为 0。这个 case 在优化前是「大 input 冷启动」，优化后同类场景不再出现极低命中。

### 3.3 dev 环境冷启动影响

优化后有 1 个 0% 命中（77027afb 的 iter1，7,070 input，0 cached），这是 dev 环境首次调用的冷启动，不是优化问题。

## 4. 结论

| 维度 | 结论 |
|------|------|
| 整体 token 缓存率 | 82.7% → 84.5%，持平 |
| 低命中 (0-20%) | 1 → 0，消除 ✅ |
| 多 iteration 稳定性 | iter3-4 稳定 99%+ ✅ |
| 退化 case | 之前独立分析 Trace C: 7.5% → 45.4% ✅ |

**核心结论**: 优化对「好 case」无负面影响，对「差 case」有显著提升。整体缓存率持平是因为该 session 本身已经是好 case。真正的收益需要看退化 case 的修复（已验证 +37.9pp）。
