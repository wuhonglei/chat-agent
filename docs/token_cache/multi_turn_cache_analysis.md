### 成因分析

**Turn 1 缓存率最高 (66.7%)：**
- system prompt + 历史消息的前缀在同会话内完全一致
- DeepSeek 的 prompt cache 对长前缀匹配效果好
- 历史消息越长，可缓存部分占比越高

**Turn 2-3 缓存率下降 (~53%)：**
- Turn 1 的完整对话（含工具返回的大段搜索结果）被追加到消息列表
- 新增内容破坏了前缀匹配，导致缓存失效
- 工具返回结果通常较大（占 prompt tokens 的 60-80%），是缓存失效的主因

**Turn 4+ 缓存率回升 (60-69%)：**
- 累积的历史上下文越来越长
- 新增的单轮对话内容占比变小
- 前缀匹配比例重新上升

## 3. 与回放测试对比

| 指标 | 回放测试 (100 questions) | 多轮对话 (20 sessions) |
|------|------------------------|----------------------|
| 调用次数 | 158 | 144 |
| 整体缓存率 | 48.8% | 52.1% |
| Per-trace 缓存率 avg | 69.5% | 58.7% |
| Per-trace 缓存率 P50 | — | 56.7% |

**差异原因：**
- 回放测试是独立单轮问答，每条 trace 的 system prompt 前缀完全一致，per-trace 缓存率高
- 多轮对话中，每一轮的消息列表随对话累积增长，前缀在轮次间不一致，per-trace 缓存率较低
- 但多轮对话的整体缓存率 (52.1%) 略高于回放测试 (48.8%)，因为多轮对话的历史消息更长，可缓存的绝对 token 数更多

## 4. 缓存率与延迟的关系

| 轮次 | 缓存率 | DeepSeek avg 延迟 |
|------|--------|------------------|
| Position 1 | 66.7% | 7.6s |
| Position 2 | 54.6% | 12.2s |
| Position 3 | 52.1% | 8.2s |

Position 2 延迟最高 (12.2s) 同时缓存率最低 (54.6%)，两者正相关：
- 缓存率低 → 更多新 token 需要计算 → 延迟更高
- Position 2 通常包含工具返回结果，prompt 膨胀是延迟增加的主因
