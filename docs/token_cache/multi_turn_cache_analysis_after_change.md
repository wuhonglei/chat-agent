## 5. 根因分析

### DeepSeek Prompt Cache 机制

- **缓存方式**: 前缀匹配 (prefix matching)
- **匹配规则**: 从第一个 token 开始连续匹配，直到出现差异
- **缓存粒度**: 请求级别的 prompt 前缀

### 为什么移到系统提示词会破坏缓存？

**【变化前】时间在用户消息中:**
```
请求 1: [system_prompt][user_msg_1 with time="03:36:17"][history_1]
请求 2: [system_prompt][user_msg_2 with time="03:36:18"][history_2]
          ~~~~~~~~~~~~~
          ↑ system_prompt 前缀完全一致 → 可缓存!
```

**【变化后】时间在系统提示词中:**
```
请求 1: [system_prompt with time="03:36:17"][user_msg_1][history_1]
请求 2: [system_prompt with time="03:36:18"][user_msg_2][history_2]
          ~~~~~~~~~~~~~~~~~~~~~~~~~~~~
          ↑ 时间不同 → 前缀不一致 → 缓存失效!
```

**关键问题**:
- 时间戳 `"03:36:17"` vs `"03:36:18"` 只差 1 秒
- 但对前缀匹配缓存来说，这是完全不同的前缀
- 结果: 100% 缓存失效

## 8. 建议方案

### 【推荐】方案 1: 保持时间在用户消息中 (恢复原状)

**文件**: `backend/app/prompts/user_prompt.py:51`

**优点**:
- 立即恢复 52% 缓存命中率
- 最小改动，风险最低
- 保持现有架构不变

**验证步骤**:
1. 确认 `user_prompt.py` 中 `<current_datetime>` 标签存在
2. 重新运行 20 组多轮测试
3. 检查 Langfuse 中 `cachedTokens > 0`

---

### 方案 2: 系统提示词中使用静态时间描述

**文件**: `backend/app/prompts/system_prompt.py`

**修改示例**:
```python
# 原来 (假设)
"当前时间是 {{ current_datetime }}，你可以获取当前时间"

# 改为
"你可以通过工具获取当前时间"  # 移除动态时间戳
```

**优点**:
- 系统提示词完全静态，100% 可缓存
- 保持"时间能力"描述在系统提示词中

**缺点**:
- LLM 需要额外调用工具获取时间 → 增加延迟和 token

---

### 方案 3: 优化系统提示词结构 (最佳实践)

**原则**: 静态内容放系统提示词，动态内容放用户消息

**实现**:
```
1. 静态系统提示词 (可缓存):
   - 角色定义
   - 工具使用规则
   - 技能描述
   - "你可以获取当前时间" (静态描述)

2. 动态用户消息 (不影响缓存):
   - 用户问题
   - 当前时间戳
   - 历史摘要
```
