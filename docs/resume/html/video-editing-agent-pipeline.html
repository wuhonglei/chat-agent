智能剪辑 Agent:Plan-Execute 架构与剪辑 DAG 设计

链路:用户上传视频素材 → Agent 理解意图 → 规划剪辑步骤 → 调用剪辑 / 特效 / 字幕工具 → 输出成品。本文以「无实际项目经验也能讲清楚」为目标,给出一套完整的架构推演:为什么选 Plan-Execute 而非纯 ReAct、Plan 如何表达为 DAG、Executor 如何调度、失败如何局部重规划,以及面试官最可能追问的 14 个问题。

1需求拆解与约束

面试第一步永远是先把问题定义清楚:输入输出是什么、约束是什么、难点在哪里。这一步决定了架构选型的论据。

输入 / 输出

输入:① 原始素材(一段或多段视频、图片、音频);② 自然语言意图,如「把这条 40 分钟的直播录像剪成 3 条 60 秒带货短视频,加字幕和热门 BGM」。

输出:符合平台规格(9:16 / 16:9、码率、时长)的成片,附带可解释的「剪辑说明」(用了哪些片段、为什么选)。

核心约束

  • 确定性:同一输入应得到稳定可复现的结果(工程上可重放);
  • 长耗时:转码/渲染是分钟级 IO+GPU 任务,不能同步阻塞;
  • 可中断恢复:失败后可从断点续跑,而不是整条链路重来;
  • 质量兜底:输出前必须有机器质检 + 可选人工确认。

难点分析(架构设计的出发点)

  • 意图模糊:「剪得精彩一点」没有客观标准 → 需要先把自然语言编译成结构化、可校验的剪辑需求(Creative Brief);
  • 素材无结构:模型无法直接「看」40 分钟视频做规划 → 需要先做素材理解,建出带时间轴的语义索引(VideoIndex);
  • 步骤间有依赖:字幕必须先有转写、混音必须在合成前 → 步骤天然构成 DAG,而不是线性链;
  • LLM 不擅长精确剪辑:「第 12.4s 到 18.7s 切一刀」这类操作必须交给确定性工具(FFmpeg 封装),LLM 只做决策、不做执行。
面试话术

「我把这个系统拆成两个世界:决策世界由 LLM 负责——理解意图、选片段、定风格,这是模糊推理问题;执行世界由确定性工具负责——剪切、转码、烧字幕,这是精确工程问题。架构的核心就是把两个世界解耦:LLM 产出一份可校验、可重放的执行计划(DAG),执行器忠实调度工具完成它。」

2端到端链路总览

六个阶段,前两个是「感知」,中间两个是「决策」,后两个是「执行与交付」。

① 素材接入
上传 / 转码 / 抽帧
② 意图理解
NL → Creative Brief
③ 素材理解
建 VideoIndex
④ Plan 生成
LLM 产出剪辑 DAG
⑤ DAG 执行
调度工具 / 产物流转
⑥ 质检交付
QC / 导出 / 人审

其中 ②③ 是可以并行启动的(用户输入意图的同时后台开始分析素材),④ 依赖 ②③ 的产物,⑤ 内部是一个 DAG 的拓扑执行,⑥ 不通过则回到 ④ 触发重规划——这个「执行 → 校验 → 必要时重规划」的闭环,就是 Plan-Execute 模式的本体。

3Plan-Execute 主架构

选型论证:为什么不用大家最熟悉的 ReAct(边想边做),而用 Plan-Execute(先规划、后执行、可重规划)。

感知输入 规划(决策世界 · LLM) 执行(工程世界 · 确定性) 校验与反馈环 交付 重规划

三个角色 + 一条反馈环

角色职责关键设计
Planner读入 Creative Brief + VideoIndex,一次性产出完整执行计划(DAG 形式的 JSON DSL),不直接碰工具。结构化输出(JSON Schema 强约束)+ 静态校验 + few-shot;规划失败直接拒绝并反问,不硬猜。
Executor对 DAG 做拓扑排序,按层并发调度工具,管理中间产物(Artifact)流转与节点状态。确定性代码,不含 LLM;支持断点续跑、重试、超时、资源(GPU)配额。
Replanner消费 Executor / Verifier 的失败报告,归因后决定:重试、换参局部重规划、还是全局重规划。只允许修改失败节点的下游子图,已成功的中间产物全部复用。
高频追问预埋:为什么不用纯 ReAct?

① 成本与延迟:ReAct 每一步都要 LLM 在环,渲染类任务动辄几十步,token 与延迟不可控;Plan-Execute 只在规划和重规划时调 LLM(本链路 2~3 次)。② 不可并发:ReAct 是串行链,而剪辑里字幕、调色、BGM 天然可并行,DAG 调度能吃掉这部分并发红利。③ 不可重放:ReAct 轨迹是模型即兴产物,出错无法断点恢复;Plan 是显式数据,可持久化、可审计、可 diff。④ 难校验:Plan 可以先做静态检查(依赖环、时间码越界、素材是否存在)再执行,ReAct 只能边错边改。结论:感知/决策用 LLM,编排用数据(Plan),执行用代码——ReAct 退化为单个决策节点内部的可选实现。

4意图理解:把自然语言编译成 Creative Brief

LLM 在这一步只做一件事:信息抽取 + 槽位填充,产出结构化 Brief。缺失关键信息就反问,而不是脑补。

用户说:「把这条直播录像剪成 3 条 60 秒抖音带货视频,节奏快一点,加字幕和热门 BGM,突出价格优惠。」

意图理解器(LLM + JSON Schema 约束解码)将其编译为右图的 CreativeBrief。所有「模糊词」都被落到可执行的数值槽位:「节奏快」→ avg_shot_len ≤ 1.8s、「突出价格」→ 高光规则中提升价格相关片段权重。

设计要点

① Brief 是后续 Planner 的唯一事实来源,字段都有默认值与合法范围;② 设置确认点(Human-in-the-loop):Brief 生成后给用户看摘要,「3 条 × 60s、快节奏、带货风」,用户确认后才进入规划——廉价的一步,挡住大部分意图偏差。

5素材理解:先建索引,再谈规划

核心论点:LLM 规划时不看视频,只看 VideoIndex——一份带时间码的多模态摘要。索引的粒度决定规划的上限。

分析通道产出实现选型(可讲)
镜头分割镜头表:scenes[],每镜 in/out 时间码、关键帧直方图/深度特征边界检测(如 TransNetV2 思路)
ASR 转写带词级时间戳的 transcript,说话人分离Whisper 系;词级对齐用于字幕断句
画面理解每镜 caption、物体/人脸/商品标签、OCR 文本抽 1~2 帧/镜 → VLM 打标;OCR 识别价格贴片
音频特征能量曲线、情绪点、静音段、BGM 区段响度/基频特征,规则即可,不上大模型
语义索引每镜 embedding 入向量库,支持「找出现价格表的镜头」式检索CLIP 类图文向量 + BM25 双路

面试话术

「素材理解是一次性成本、多次复用:建索引花 5 分钟,但用户之后说『再来一版抒情的』时,Planner 直接复用索引重新规划,秒级出新 Plan。这就是把感知层和决策层解耦的复利。」

6Planner:Plan 即 DAG

Planner 的输出不是散文,而是一份 JSON DSL——节点是工具调用、边是数据依赖。它同时是「计划」「契约」和「可持久化的中间表示」。

{
  "plan_id": "pln_7f2a", "version": 3,
  "nodes": [
    { "id": "select",  "tool": "clip_selector",
      "params": { "rules": "$brief.highlight_rules", "top_n": 12 } },
    { "id": "roughcut", "tool": "ffmpeg.concat",
      "params": { "clips": "$select.output.clips", "max_shot": 1.8 } },
    { "id": "subtl",   "tool": "subtitle.timeline",
      "params": { "asr": "$index.transcript", "clips": "$select.output.clips" } },
    { "id": "burnin",  "tool": "subtitle.burn",
      "params": { "video": "$roughcut.output", "srt": "$subtl.output",
                  "style": "$brief.style.subtitle.style" } },
    { "id": "qc",      "tool": "qc.check",
      "params": { "video": "$compose.output", "rules": ["av_sync","blackframe"] } }
  ],
  "edges": [
    ["select","roughcut"], ["select","subtl"],
    ["roughcut","burnin"], ["subtl","burnin"]
  ]
}

四层防护,治「LLM 输出不可靠」

  • ① Schema 层:JSON Schema 约束解码(function calling / guided decoding),语法层面保证可解析、字段齐全、枚举合法;
  • ② 静态校验层:确定性代码检查——DAG 无环(拓扑可排序)、$ref 引用存在、时间码不越界、工具名在注册表内、参数类型匹配;
  • ③ 语义护栏层:用少量规则兜底,如「成片时长必须落在 brief.duration_sec 区间」「所选片段总时长 ≥ 成片时长」;违规则打回 Planner 并附错误信息(self-correction);
  • ④ 模板兜底层:对高频任务(高光再剪、口播切片)预置参数化 Plan 模板,LLM 只填槽位——把生成问题降级为抽取问题,成功率接近 100%;自由任务才走全量生成。
关键认知

信任不是来自「模型很强」,而是来自「错误在执行前能被拦住」。静态校验不过 → 错误信息回喂 Planner 重出,最多 N 轮 → 仍不过则请求人审。这是把 LLM 放进生产系统的通用范式。

7执行 DAG 全景图

以「直播录像 → 3 条带货短视频」为例的完整剪辑 DAG。两条子链(画面链 / 声音链)在「终合成」汇合,质检挂在最后——这是典型的分叉-汇合(fork-join)结构。

感知产物 决策节点(LLM 参与) 画面链(确定性工具) 声音链(确定性工具) 合成 / 交付 质检(可触发 Replan)

拓扑分层(Executor 的并发依据)

层节点说明
L1N1 高光选择 ∥ N3 字幕时间轴互不依赖,并行启动
L2N2 粗剪 ∥ N5 BGM 匹配N2 等 N1;N5 等 N1
L3N7 调色 ∥ N6 混音N6 等 N2+N5
L4N4 字幕烧录等 N7+N3(汇合点)
L5~L7N9 合成 → N10 质检 → N11 导出串行收尾

这张图能讲出的三个加分点

  • 汇合点设计:N4、N9 是 fork-join 的 join 点,Executor 必须支持「多入边全部就绪才触发」——不是简单队列能搞定的;
  • 关键路径:N1→N2→N7→N4→N9→N10→N11,约占总时长 85%;声音链是非关键路径,调度器可让 GPU 优先供给关键路径节点;
  • 重规划局部性:若 N10 报「字幕样式溢出」,只需重跑 N4 子树(N4→N9→N10),N2/N7 的产物直接复用——省 70% 重算。

8Executor:DAG 调度器

Executor 是确定性代码,不含模型。核心循环:找就绪节点 → 派发执行 → 落产物 → 推进状态 → 失败转 Replan。

class DagExecutor:
    def run(plan):
        state = PlanState.load(plan.plan_id)          # 断点恢复:已 SUCCESS 的节点直接跳过
        while not state.all_terminal():
            ready = topo_ready_nodes(plan, state)      # 入边全部 SUCCESS 的 PENDING 节点
            for node in schedule(ready, key=critical_path_first):  # 关键路径优先 + GPU 配额
                if node.id in plan.human_gates:       # 人审节点:挂起等确认(如粗剪确认)
                    state.mark(node, WAITING_HUMAN); continue
                submit(node, to=tool_router(node))     # 按工具类型路由到 CPU/GPU/LLM 队列
            ev = event_queue.poll(timeout=HEARTBEAT)   # 事件驱动:完成/失败/进度
            if ev.type == SUCCESS:
                artifact_store.put(ev.node_id, ev.output_uri, meta=ev.meta)  # 产物注册(含血缘)
                state.mark(ev.node_id, SUCCESS)
            elif ev.type == FAILED:
                policy = retry_policy(ev.error)        # 瞬时错误:指数退避重试 ≤3 次
                if policy.exhausted:
                    report = FailureReport(ev.node_id, ev.error, trace=state.trace)
                    return replanner.handle(report)  # 移交重规划器,附完整上下文
            elif ev.type == TIMEOUT:
                cancel(ev.node_id); return replanner.handle(timeout_report(ev))
        return artifact_store.get(plan.sink_node)

幂等与重放

每个节点的输出路径由 hash(plan_id, node_id, params) 决定:同参数重跑直接命中缓存产物,天然支持断点续跑与「换参数重规划」的差异化复用。

资源调度

渲染/烧录是 GPU 任务,转写/LLM 是 API 任务,调度器按队列分类限速;长任务用心跳 + 检查点,进程崩溃后可从最近检查点恢复。

事件溯源

所有状态迁移写事件流(Kafka / 本地 WAL),Plan 的当前状态是事件重放的结果——审计、回放、埋点统计(哪类节点最爱失败)都来自它。

9工具层与产物协议

工具层的两条铁律:工具不读文件路径之外的「隐式状态」、一切输入输出都是注册的 Artifact。这样 DAG 才可在任意机器上重放。

统一工具协议(Tool Contract)

{
  "tool": "subtitle.burn",
  "schema": { "in": { "video": "artifact:video", "srt": "artifact:text", "style": "enum" },
              "out": { "video": "artifact:video" } },
  "runtime": { "queue": "gpu", "timeout": 600, "idempotent": true },
  "impl": "ffmpeg -i {video} -vf subtitles={srt}:force_style=... "
}

Planner 只能引用注册表内的工具与字段;Executor 在执行前把 $ref 解析为真实产物 URI。工具对 LLM 是黑盒 API,对工程是确定性函数。

工具注册表(示例裁剪)

工具类型队列
ffmpeg.cut / concat / compose画面CPU/GPU
effect.lut / transition / sticker画面GPU
subtitle.timeline / burn字幕CPU
audio.mix / loudnorm声音CPU
clip_selector / bgm_search决策LLM/检索
qc.check(规则+ VLM)质检混合
Artifact Store 的血缘价值

每个产物记录 {由哪个节点、哪个 plan 版本、什么参数、哪些上游产物} 生成。收益:① 重规划时精准判断哪些产物可复用;② 成片可追溯——「这条字幕为什么错了」能一路追到 ASR 的原始转写;③ 质检报告与成片版本绑定,支撑线上质量看板。

10Replanner:失败归因与局部重规划

Plan-Execute 的灵魂在「Re」。不是所有失败都值得惊动 LLM——先按失败类型分级,能工程解决的不上模型。

失败类型例子策略重跑范围
瞬时错误网络抖动、GPU OOM 偶发、限流指数退避重试(≤3 次),不改动 Plan单节点
参数错误字号过大导致字幕溢出、转场时长超过相邻镜头Replanner 只调失败节点参数(规则或 LLM 小改)失败节点 + 下游子图
结构错误QC 连续不通过:选段与 Brief 目标不符、混音盖过人声LLM 重新生成受影响子图(如重选 BGM、重选片段),上游产物复用子图替换
需求冲突素材只有 50s 有效内容却要剪 60s、素材与意图不匹配全局重规划或升级人审,附「冲突说明」让用户改 Brief整 Plan / 回到用户

子图替换怎么做到「只重跑必要的」

① 由失败节点沿出边求受影响闭包;② 闭包内节点标记 STALE,产物作废;③ 闭包外的 SUCCESS 产物全部保留;④ Replanner 生成的新子图做接口对齐校验(输入类型/时间基准必须与原图一致)后缝合进原 Plan,version + 1 重入 Executor。

防死循环

给每个 Plan 设 replan_budget(如 ≤3 次、重算成本 ≤ 原始 50%);预算耗尽或同一节点失败两次即升级人审。止损本身就是一种架构能力——线上系统不能允许 Agent 无限自我纠正。

11观测、成本与扩展

成本控制

  • LLM 调用仅 2~3 次/任务:Brief 抽取、Plan 生成、(可选)Replan——感知全部用小模型/规则;
  • 模型分级:Brief/校验用 7B 级,Plan 生成用旗舰模型;
  • 产物缓存:同素材 + 同参数命中 Artifact 缓存,二次创作(换风格)零重渲染成本只发生在差异子图。

质量评估(怎么知道剪得好)

  • 规则 QC:音画同步漂移、黑帧/静帧、响度、时长合规、字幕越界;
  • 模型 QC:VLM 抽帧打分(构图、字幕可读性)、ASR 回检成片音轨;
  • 业务指标:一次通过率(first-pass yield)、平均 Replan 次数、人审修改率——这些就是面试里该报的「北极星」。

向多 Agent 演进

  • 按工种拆:编导 Agent(Brief+选段)、剪辑 Agent(画面链)、包装 Agent(字幕/特效)、审片 Agent(QC);
  • 单 Agent 的 Planner 退化为「总编导」,各工种 Agent 持有自己的子 DAG;
  • 但协议不变:Agent 间仍用 Plan/Artifact 通信——先单机跑通,再拆服务。
面试收尾话术(30 秒总结)

「这套设计的本质是分层解耦:感知层把视频变成数据(VideoIndex),决策层把意图变成计划(CreativeBrief → Plan/DAG),执行层把计划变成产物(Executor + 工具协议),反馈层把产物质量变回计划修正(Verifier → Replanner)。LLM 只出现在它擅长的模糊推理位置,一切确定性的东西都交给代码——所以它可重放、可断点恢复、可局部重规划,也能讲清楚每一分钱花在哪儿。」

12面试高频追问 Q&A

点击展开。每一条都按「先结论、再给机制、最后给数字感」的方式回答。

什么场景下 ReAct 搞不定、必须用 Plan-Execute?你的项目为什么选 ReAct?

答题关键:不要踩一捧一,证明你理解两者的适用边界——选哪个都有论据。一句话分界:当任务「步骤多、可并行、失败代价高、要求可复现」时,ReAct 的四个基因缺陷会同时爆发。

场景特征ReAct 为什么崩剪辑链路的对应点
长程任务(几十步+)上下文越堆越长,早期决策被挤出窗口,后期动作漂移;每步一次 LLM 调用,token 与延迟线性爆炸剪辑链路 10+ 节点,ReAct 要 30~50 次模型调用,Plan-Execute 只要 2~3 次
步骤可并行严格串行的 thought→action→observation 链,物理上无法表达「字幕和调色同时做」字幕时间轴、BGM、调色互不依赖,串行白扔 40% 延迟
失败代价高轨迹是模型即兴产物,第 20 步挂了无法「只重跑 18~20 步」,只能整条重来烧字幕样式错了只需重跑 N4 子树;重放轨迹 = 全片重渲
执行前需校验边做边错边改,没有「整体计划」可供静态检查Plan 可先查依赖环、时间码越界、工具是否存在

本质差异:ReAct 的计划是隐式的(藏在模型脑子里),Plan-Execute 的计划是显式的(可持久化、可 diff、可审计的数据)。

而我的对话式 Agent 平台选 ReAct,是用同一把尺子量出来的:① 对话是短视域任务,3~8 步收敛,上下文压力到不了临界点;② 强交互弱结构,用户每轮都可能改方向,ReAct 每步可被打断纠偏,Plan-Execute 改需求等于作废整份 Plan;③ 延迟敏感,ReAct 首步动作一个 RTT 就出去,流式 thought 还能当加载动画;④ 对话任务下一步依赖上一步观察,本来就是串行数据依赖,DAG 调度没有并行红利可吃。

收口:「ReAct 和 Plan-Execute 不是替代关系,是任务时域的分界:交互式、短程、探索性任务用 ReAct;批处理式、长程、结构化任务用 Plan-Execute。成熟系统里两者嵌套——我的对话平台遇到重度任务(如一键生成网页)时,也是把重活摘出来走预定义 workflow,而不是硬让 ReAct 跑五十轮。」

用户说「剪成 30s 短片并加字幕」,Agent 怎么规划?失败一步怎么局部重试?

① 意图编译:LLM 做槽位填充产出 Brief(duration ∈ [28,32]s、subtitle=on)。加分点:缺槽不脑补——「30s 从 40 分钟里选什么内容?什么比例?」要么走默认高光策略,要么反问一句,Agent 要知道什么时候不该自作主张。

② 生成 Plan:基于已建好的 VideoIndex(一次性成本)产出 DAG——N1 高光选段(产出 EDL,约束总时长 28~32s)∥ N2 字幕时间轴(词级 transcript 断句出 SRT)→ N3 粗剪等 N1、N4 字幕烧录等 N2+N3(汇合点)→ N5 质检(音画同步/时长/字幕越界)→ N6 导出。

③ 局部重试(题眼,按失败类型分四层,最忌讳一句「重新跑一遍」):

  • L1 瞬时错误(FFmpeg OOM、上传超时):指数退避重试 ≤3 次,节点幂等(输出路径 = hash(plan_id, node_id, params))重跑无脏数据——完全不惊动 LLM;
  • L2 参数错误(字幕超出安全框):Replanner 只改 N4 参数(字号/每行字数),N4→N5→N6 标记 STALE 重跑,N1/N2/N3 产物全部复用,重算成本仅 ~30%;
  • L3 结构错误(成片只有 24s 不达标):沿 N1 出边求受影响闭包(含 N2,选段变了 SRT 也要重算)→ 闭包外产物保留 → LLM 重新生成选段子图(放宽阈值/补次优片段)→ 接口对齐校验后缝合,plan.version+1 重入 Executor;
  • L4 需求冲突(素材有效内容仅 20s):重试解决不了,附冲突说明回到用户:「建议放宽到 20s,或允许循环/慢放补时长」。

兜底:replan_budget(重规划 ≤3 次、重算成本 ≤ 原始 50%),同一节点失败两次升级人审。收口:「局部重试的本质是——Plan 是数据、产物有血缘、失败可归因,所以系统能精确算出最小重跑集合;四层策略只有 L3 需要 LLM,其余全是确定性工程,这就是成本和稳定性的来源。」

如果素材理解错了(比如 ASR 转错、镜头分错),下游不是全错了吗?

会,所以感知层要有置信度:每条 transcript、每个镜头边界都带 score。Planner 在高光选择时对低置信片段降权;QC 阶段用「成片音轨回检 ASR」与索引交叉验证,不一致则触发感知层局部重建(只重跑对应时间段的分析)。另外关键设计是索引可增量更新:重跑某段 ASR 不影响其它镜头。

LLM 生成 Plan 时幻觉了一个不存在的工具怎么办?

三层拦截:① 约束解码时工具名走枚举,语法层面就生成不出表外工具;② 静态校验查注册表,命中幻觉工具则把「可用工具清单 + 错误信息」回喂重出;③ 高频任务走参数化模板,LLM 只填槽不选工具。真正兜底的是:Plan 不过静态校验就不允许执行,幻觉只能造成重试,不能造成事故。

用户中途改需求(「不要 3 条了,要 1 条 3 分钟的」)怎么处理?

把「改需求」建模为 Brief 的 diff,而不是新任务:① Brief diff → 受影响的 Plan 节点集合(如选段数量、时长约束变了 → select 节点参数变);② 未受影响的产物(素材索引、已完成与 diff 无关的节点)全部复用;③ 等价于一次「用户触发的局部重规划」。这也是为什么 Plan 必须是显式数据——diff 一个 DAG 远比 diff 一段 ReAct 轨迹容易。

执行时间这么长(分钟级),用户就干等着吗?

① 全异步:提交即返回 plan_id,前端轮询/WebSocket 推节点进度(DAG 图本身就是最好的进度可视化——直接复用第 7 节那张图染状态色);② 分级交付:先出低码率预览版(快编管线,30s 内),确认后再跑高质量渲染;③ 人审节点(粗剪确认)天然打断等待,把等待变成交互。

并发度怎么控制?100 个用户同时提交呢?

Executor 不直接执行,只向分类队列(CPU / GPU / LLM-API)投递,各队列按 worker 池和消费速率限流;单 Plan 内并发度由拓扑分层决定(本例最多 2 路),再叠加租户级配额防止单用户打爆 GPU 池。优先级用「关键路径优先 + 预览版插队」,避免短任务被长任务饿死。

「精彩片段选择」这种主观决策,怎么保证质量?

不承认它纯主观,把它拆成可量化的代理信号加权:关键词命中(价格/卖点)、音频能量峰值、语速变化、画面运动幅度、VLM 构图分。LLM 的角色是「根据 Brief 调权重 + 从 top-N 候选里做最终取舍并给出理由」。同时保留人审点和 A/B:线上用点击率/完播率回流校准权重——这是推荐系统的思路搬到剪辑上。

为什么 QC 要同时用规则和 VLM?只用一个不行吗?

两类错误正交:规则擅长客观硬伤(音画漂移 300ms、响度超标、黑帧)——便宜、确定、可解释,但不理解「美」;VLM 擅长语义问题(字幕压住人脸、构图歪斜、贴纸违和)——但有幻觉、成本高。所以规则做硬门禁(不通过必 Replan),VLM 做软评分(低于阈值触发人审)。成本上,VLM 只抽关键帧而非全片。

这套架构里最有风险的地方是什么?(压力题)

讲真话说两个:① Planner 的 Plan 质量——它决定了 DAG 结构本身对不对,缓解手段是模板兜底 + 静态校验 + 人审门禁,但「创意好不好」仍依赖模型能力,所以要留人审;② 索引粒度与成本的矛盾——镜头级索引够不够用、要不要秒级/帧级,直接决定感知成本翻倍与否,工程上按任务类型分级建索引(快剪用粗索引,精剪再补细粒度)。承认边界、给出权衡,比声称「都能解决」更像做过系统的人。

和直接调一个「视频生成大模型」端到端出片相比,优势是什么?

① 可控可编辑:每个中间产物可单独替换(换 BGM 不用重生成全片);② 保真:素材是用户真实内容,不能允许生成模型「重画」商品和口型——剪辑是组合问题不是生成问题;③ 成本:端到端视频生成按时长计费,成本高 1~2 个数量级;④ 可审计:每个决策有迹可循。生成模型在本架构里的正确位置是工具层的一员(如生成转场动画、补帧),而不是取代管线。

Plan 存哪里?长任务做到一半服务重启怎么办?

Plan(JSON)+ 事件流持久化到存储(MySQL/对象存储),节点状态由事件溯源重建;Worker 崩溃后,心跳超时的节点重新入队,幂等产物路径保证重跑不产生脏数据;调度器重启时 replay 事件流恢复全部在途 Plan 状态。核心思想:内存里没有不可丢失的东西。

没有真实项目,怎么让面试官相信你能落地?

① 讲取舍不讲名词:为什么 Plan-Execute 而不是 ReAct、为什么索引先行、为什么 LLM 不进执行路径——每个选择都有被否决的备选方案;② 讲失败模式:幻觉工具、时长冲突、子图重跑、防死循环——没踩过坑的人讲不出失败清单;③ 讲数字感:LLM 调用次数、关键路径占比、缓存命中率、replan 预算;④ 主动给演示:现场画出第 7 节那张 DAG,然后指着图讲 fork-join 和局部重规划。
