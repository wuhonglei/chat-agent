# 图片 Token 计算公式验证报告

## 背景

项目中 `TokenCalculator` 使用 GPT-4V 风格的公式估算图片 token 数：

```python
# backend/app/utils/token.py
IMAGE_PATCH_SIZE = 28
IMAGE_FIXED_TOKEN_OVERHEAD = 2

tokens = ceil(height / 28) * ceil(width / 28) + 2
```

当前项目实际调用的是 Qwen 系列模型（qwen3.7-plus，通过 DashScope API）。需要验证该公式对 Qwen 模型是否准确。

## 测试方法

1. 将图片编码为 data URL 发送给 API
2. 同时发送纯文本请求作为基线
3. `图片实际 token = 含图片请求的 prompt_tokens - 纯文本基线的 prompt_tokens`

## 测试结果

| 图片 | 尺寸 | 原始像素 | 实际 token | 项目公式估算 | 误差 |
|------|------|----------|-----------|-------------|------|
| 真实截图 | 3526×2240 | 7,898,240 | 2522 | 10082 | -75.0% |
| 纯色图 | 4096×2160 | 8,847,360 | 2486 | 11468 | -78.3% |
| 纯色图 | 2048×1536 | 3,145,728 | 2496 | 4072 | -38.7% |
| 纯色图 | 1024×1024 | 1,048,576 | 1026 | 1371 | -25.2% |
| 纯色图 | 512×512 | 262,144 | 258 | 363 | -28.9% |
| 纯色图 | 256×256 | 65,536 | 66 | 102 | -35.3% |

## 结论

### 1. 项目公式严重高估（总误差 18,604）

GPT-4V 公式直接用原始图片尺寸计算 patch 数，但 Qwen API 会在服务端对图片进行预处理（缩放），导致原始尺寸与实际参与 token 计算的尺寸差异很大。

### 2. 大图（>2M 像素）：API 会缩放到约 200 万像素

三个原始尺寸差异巨大的图片，API 返回的 token 数几乎相同：

```
3526×2240 (7.9M px) → 2522 tokens
4096×2160 (8.8M px) → 2486 tokens
2048×1536 (3.1M px) → 2496 tokens
```

反推过程：token ≈ 2500，patch size = 28

```
(w/28) * (h/28) ≈ 2500
有效像素 ≈ 2500 * 28² = 1,960,000 ≈ 2M px
```

对应 Qwen2-VL 的默认 `max_pixels` 配置：

```python
max_pixels = 1280 * 28 * 28 = 1,003,520  # Qwen2-VL 默认值
# DashScope API 实际使用约 2560 * 28² = 2,007,040
```

验证（等比缩放 + 对齐到 28 的整数倍）：

```
3526×2240: scale = √(2007040/7898240) = 0.5072
  → 1788×1136 → 对齐 1764×1120 → (1764/28)×(1120/28) = 63×40 = 2520 ✅

4096×2160: scale = √(2007040/8847360) = 0.4764
  → 1951×1029 → 对齐 1932×1008 → (1932/28)×(1008/28) = 69×36 = 2484 ✅

2048×1536: scale = √(2007040/3145728) = 0.7997
  → 1638×1228 → 对齐 1624×1204 → (1624/28)×(1204/28) = 58×43 = 2494 ✅
```

大图的有效公式为：

```python
# 先缩放到 max_pixels 以内
if w * h > 2_007_040:
    scale = sqrt(2_007_040 / (w * h))
    w, h = int(w * scale), int(h * scale)

# 对齐到 28 的整数倍
w = (w // 28) * 28
h = (h // 28) * 28

tokens = (w / 28) * (h / 28) + 2
```

### 3. 小图（<2M 像素）：行为不一致

小图不做缩放（原始像素 < max_pixels），但实际 token 比直接用 28x28 patch 计算的少约 26%：

| 图片 | 原始像素 | 实际 token | 28×28 不缩放 | 32×32 不缩放 |
|------|----------|-----------|-------------|-------------|
| 1024×1024 | 1,048,576 | 1026 | 1370 | **1026** |
| 512×512 | 262,144 | 258 | 324 | **258** |
| 256×256 | 65,536 | 66 | 82 | **66** |

小图的数据恰好匹配 32×32 patch size（`(w/32)*(h/32)+2`），但大图不适用该公式。推测 API 可能根据图片分辨率动态调整 patch size 或编码策略，具体机制需进一步验证。

## 建议

当前项目公式 `ceil(h/28)*ceil(w/28)+2` 对 Qwen 模型误差过大（平均 ~50%），建议修正：

1. **如果只关心上下文窗口预算**（高估更安全）：当前公式可保留，但需知会高估 2-4 倍
2. **如果需要精确估算**：需按模型类型区分公式，或改为调用 API 获取实际 usage
3. **最小改动方案**：在估算前先对大图做 max_pixels 缩放，可消除大图的 75% 误差
