# GEO AI 搜索优化平台 — 技术反思与演进部门实现建议

---

## 一、当前架构复盘与关键瓶颈识别

### 1.1 现有链路回顾

```
关键词库 → 采样任务分发(Kafka) → Playwright采集引擎 → 数据清洗/存储 → Portal运营分析
```

### 1.2 已验证有效的核心能力

| 能力 | 当前状态 | 成熟度 |
|------|----------|--------|
| 多平台模拟交互采集 | 已落地 | ⭐⭐⭐⭐ |
| 反爬与恢复策略 | 已落地 | ⭐⭐⭐⭐ |
| 可观测体系 | 已落地 | ⭐⭐⭐ |
| 账号生命周期管理 | 已落地 | ⭐⭐⭐ |
| Agent驱动的闭环优化 | 规划中 | ⭐ |

### 1.3 向Agent化演进的核心挑战

1. **数据质量到决策质量的gap**：当前采集的是"AI说了什么"，但Agent需要的是"AI为什么这样说"（信源权重、引用逻辑）
2. **Actionable闭环缺失**：从"发现问题"到"解决问题"仍依赖人工运营介入
3. **多Agent协作框架未建立**：关键词研究、内容生成、发布、效果监控是独立模块，缺乏编排

## 二、Agent化GEO闭环架构设计

### 2.1 目标架构（"监控-分析-优化"完整闭环）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          GEO Agent Orchestrator                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐    │
│  │ 监控Agent   │→ │ 分析Agent   │→ │ 决策Agent   │→ │ 执行Agent       │    │
│  │ (Monitor)   │  │ (Analyzer)  │  │ (Planner)   │  │ (Executor)      │    │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘  └────────┬────────┘    │
│         │                │                │                  │             │
│         └────────────────┴────────────────┴──────────────────┘             │
│                              ↑ 反馈回路                                     │
└─────────────────────────────────────────────────────────────────────────────┘
                                      │
┌─────────────────────────────────────┼─────────────────────────────────────┐
│           数据底座（现有能力复用）     │                                     │
│  ┌─────────────┐  ┌─────────────┐   │   ┌─────────────────────────────┐  │
│  │ Playwright  │  │ 结构化存储   │   │   │ 内容发布平台（TikTok/      │  │
│  │ 采集引擎    │→ │ (MySQL/ES)  │───┘   │ Shopee Feed/博客等）        │  │
│  │ (已落地)    │  │ (已落地)    │       │ (待对接)                    │  │
│  └─────────────┘  └─────────────┘       └─────────────────────────────┘  │
└───────────────────────────────────────────────────────────────────────────┘
```

### 2.2 各Agent职责与输入输出定义

#### 监控Agent (Monitor Agent)

| 维度 | 说明 |
|------|------|
| **输入** | Playwright采集的原始渲染结果（HTML/DOM快照） |
| **核心能力** | ① 品牌提及检测（Shopee品牌名、商品名、店铺名）<br>② 推荐位次提取（第几位被推荐）<br>③ 竞品对比（与Lazada/Tokopedia等竞品同屏出现时的相对位置）<br>④ 信源溯源（AI引用了哪些网页/内容作为依据） |
| **输出** | 结构化监控事件：`{keyword, platform, brand_mentions: [{position, context, source_url}], competitor_mentions, timestamp}` |
| **触发条件** | 定时采样完成 / 异常阈值告警 |

#### 分析Agent (Analyzer Agent)

| 维度 | 说明 |
|------|------|
| **输入** | 监控Agent输出的结构化事件流 + 历史趋势数据 |
| **核心能力** | ① 趋势分析（品牌曝光率周环比/月环比）<br>② 根因分析（曝光下降时，定位是信源减少？竞品内容增加？AI算法调整？）<br>③ 机会识别（高搜索量但低曝光的关键词 = 优化机会）<br>④ 竞品策略反推（竞品在哪些信源上被频繁引用） |
| **输出** | 分析报告：`{insight_type, severity, root_cause, affected_keywords, recommended_actions}` |
| **关键技术** | LLM + RAG（接入内部知识库：历史优化案例、平台算法更新记录） |

#### 决策Agent (Planner Agent)

| 维度 | 说明 |
|------|------|
| **输入** | 分析Agent的报告 + 运营策略约束（预算、优先级、合规要求） |
| **核心能力** | ① 关键词优先级排序（高流量×低曝光×低竞争 = 优先优化）<br>② 内容策略生成（针对特定关键词，决定是优化现有内容还是创建新内容）<br>③ 发布渠道选择（TikTok短视频？Shopee Feed？博客文章？）<br>④ 资源分配（人力、预算、时间窗口） |
| **输出** | 可执行计划：`{tasks: [{keyword, action_type, content_brief, target_platform, deadline, owner}]}` |
| **关键技术** | ReAct Loop（Reasoning + Acting）+ 多目标优化算法 |

#### 执行Agent (Executor Agent)

| 维度 | 说明 |
|------|------|
| **输入** | 决策Agent生成的任务计划 |
| **核心能力** | ① 内容自动生成（商品标题优化、营销文案、短视频脚本）<br>② 多平台发布（对接TikTok API、Shopee Seller API、CMS系统）<br>③ A/B测试配置（同一关键词生成多版本内容，分流测试）<br>④ 发布状态同步 |
| **输出** | 执行结果：`{task_id, content_url, publish_status, publish_time}` |
| **关键技术** | LLM内容生成 + MCP协议对接各平台API |

## 三、分阶段演进路线图

### Phase 1: 数据增强（1-2个月）—— 夯实Agent的数据底座

当前采集的是"AI回复的渲染结果"，但Agent需要更深层的结构化信息。建议优先补齐以下数据维度：

| 新增数据维度 | 采集方式 | 优先级 | 说明 |
|-------------|---------|--------|------|
| **信源URL提取** | Playwright DOM解析 | P0 | AI回复中引用的网页链接（通常以脚注/卡片形式呈现），这是GEO优化的核心靶点 |
| **引用内容片段** | 结合信源URL二次抓取 | P0 | AI引用了该网页的哪段内容，帮助理解AI的"引用偏好" |
| **竞品同框数据** | 同屏OCR/文本提取 | P1 | 同一回复中Shopee与竞品同时出现时的相对位置、评价倾向 |
| **多轮对话上下文** | 模拟追问链 | P1 | 用户追问后AI推荐是否变化，反映AI的"记忆/偏好" |
| **地域/语言维度** | 代理IP切换 + 语言参数 | P2 | 不同国家站点的AI回复差异（SG/MY/PH/ID等） |

**技术实现建议**：
- 在现有Playwright采集链路中增加`DOM解析层`，提取`<a>`标签的href、引用卡片的数据属性
- 新增`Source Crawler`微服务，对提取的信源URL进行异步抓取和内容快照存储
- 数据模型扩展：在现有MySQL schema中新增`ai_sources`表，关联到每次采样记录

```sql
-- 建议新增表结构
CREATE TABLE ai_sources (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    sample_id BIGINT NOT NULL,
    source_url VARCHAR(2048) NOT NULL,
    source_title VARCHAR(512),
    cited_text TEXT,           -- AI引用的具体片段
    source_domain VARCHAR(255), -- 域名，用于聚合分析
    position_in_reply INT,      -- 在回复中的引用顺序
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_sample_id (sample_id),
    INDEX idx_domain (source_domain)
);
```

### Phase 2: 分析Agent MVP（2-3个月）—— 从"看数据"到"读数据"

目标：让系统能自动回答"为什么曝光下降了"

**核心能力建设**：

1. **品牌曝光趋势自动归因**
   ```
   输入：近30天品牌曝光率时间序列
   输出：归因报告

   归因维度：
   - 信源维度：被引用的信源数量变化？信源质量变化？
   - 竞品维度：竞品内容新增量？竞品信源抢占？
   - 平台维度：AI算法更新？（需接入外部GEO行业情报源）
   - 内容维度：我方内容老化？（信源内容更新频率下降）
   ```

2. **关键词机会评分模型**
   ```
   机会分数 = 搜索量 × (1 - 当前曝光率) × 竞争强度系数 × 商业相关性

   自动输出"Top 20 优先优化关键词"
   ```

3. **RAG知识库搭建**
   - 向量数据库（建议接入内部已有的ES或引入专用向量DB如Milvus）
   - 知识来源：历史优化案例、平台算法更新公告、竞品分析报告
   - 分析Agent在生成报告时自动检索相似历史场景

**技术选型建议**：
- LLM：内部已有模型优先，如无则考虑Claude/GPT-4 API（注意数据合规）
- RAG框架：LangChain / LlamaIndex（与现有NestJS后端集成）
- 向量存储：Elasticsearch（如已有）或 Pinecone/Milvus

### Phase 3: 决策与执行Agent（3-4个月）—— 闭环自动化

目标：实现"发现问题 → 生成方案 → 自动执行 → 效果追踪"的无人值守闭环

**决策Agent核心逻辑**：
```
ReAct Loop 示例：

Thought: 关键词"best online shopping app"近7天曝光率从15%降至5%
Action: 查询该关键词的历史信源分布
Observation: 信源从12个降至3个，且主要信源为竞品博客
Thought: 需要补充该关键词相关的高质量内容
Action: 生成内容策略（博客文章 + TikTok视频）
Observation: 策略已生成，预估投入X，预期回报Y
Thought: 策略ROI符合阈值，批准执行
Action: 调用执行Agent发布内容
```

**执行Agent能力建设**：

| 能力 | 实现方式 | 依赖 |
|------|---------|------|
| 商品标题优化 | LLM Prompt Engineering + 内部商品数据 | 商品中心API |
| 营销文案生成 | 基于Shopee品牌调性的Fine-tuned模型 | 品牌素材库 |
| 短视频脚本 | LLM生成 + 内部视频模板 | 创意中心 |
| 多平台发布 | MCP协议封装各平台API | TikTok/Shopee/博客API |
| A/B测试 | 分流发布 + 采样效果追踪 | 现有采集链路复用 |

**人机协作边界设计**（关键！）：
- 全自动：常规关键词优化、内容更新
- 人工审批：高预算投入、品牌敏感内容、新平台首次发布
- 人工介入：异常告警、策略冲突、合规审查

### Phase 4: 效果验证与迭代（持续）

- 闭环效果指标：从"内容发布"到"AI回复中品牌曝光提升"的转化率和时滞
- 建立"内容-信源-曝光"的归因链路，验证哪些内容策略真正有效
- Agent自我优化：基于执行效果反馈，自动调整决策策略（RLHF）

## 四、关键技术决策建议

### 4.1 Agent框架选型

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| **LangChain + 自建Orchestrator** | 生态成熟，与NestJS集成友好 | 抽象层较厚，学习成本 | **推荐** — 适合已有Node.js技术栈的团队 |
| **AutoGen (Microsoft)** | 多Agent对话编排能力强 | 生态较新，Python为主 | 如团队有Python能力可考虑 |
| **自建ReAct框架** | 完全可控，无外部依赖 | 开发成本高 | 如内部已有Agent框架基础，可复用 |
| **Dify/Flowise等低代码** | 快速验证 | 扩展性受限 | 仅适合MVP快速验证 |

**建议**：基于现有NestJS后端，引入LangChain.js作为Agent编排层，保持技术栈统一。

### 4.2 与现有系统的集成点

```
┌────────────────────────────────────────────────────────────┐
│                    现有系统（已落地）                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐ │
│  │ NestJS BFF  │  │ Kafka队列   │  │ MySQL + Redis       │ │
│  │ Portal API  │  │ 任务分发    │  │ 数据存储            │ │
│  └──────┬──────┘  └──────┬──────┘  └──────────┬──────────┘ │
│         │                │                    │            │
│         └────────────────┴────────────────────┘            │
│                         ▼                                  │
│              ┌─────────────────────┐                       │
│              │   Agent Orchestrator │ ← 新增层              │
│              │   (LangChain.js)     │                       │
│              └─────────────────────┘                       │
│                         │                                  │
│         ┌───────────────┼───────────────┐                  │
│         ▼               ▼               ▼                  │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐          │
│  │ Monitor     │ │ Analyzer    │ │ Executor    │          │
│  │ Agent       │ │ Agent       │ │ Agent       │          │
│  └─────────────┘ └─────────────┘ └─────────────┘          │
└────────────────────────────────────────────────────────────┘
```

**关键集成原则**：
1. **复用现有采集链路**：Playwright采集引擎无需重构，只需增加DOM解析和数据输出格式
2. **复用Kafka消息队列**：Agent任务通过现有Kafka Topic分发，利用已有的并发控制和暂停/恢复机制
3. **复用可观测体系**：Agent执行日志接入现有Prometheus/Grafana监控
4. **Portal扩展**：在现有Portal上新增"Agent策略配置"和"自动化报告"模块

### 4.3 数据安全与合规

GEO采集涉及模拟真实用户与AI平台交互，需特别注意：

| 风险点 | 缓解措施 |
|--------|---------|
| 账号封禁风险 | 延续现有"代理摘除+动态冷却"策略；增加Agent行为随机化（模拟真实用户浏览模式） |
| 数据隐私 | 采集数据脱敏处理；不存储用户PII；符合各站点隐私政策 |
| API调用合规 | 使用官方API优先（如OpenAI API用于内容生成），模拟交互仅用于数据采集 |
| 内容版权 | 自动生成内容需通过内部合规审查；引用第三方内容需标注来源 |

## 五、可量化的演进目标

| 阶段 | 时间 | 目标指标 |
|------|------|---------|
| Phase 1 | 1-2月 | 信源提取覆盖率 > 90%；数据结构化率 100% |
| Phase 2 | 3-5月 | 分析报告自动生成率 > 80%；归因准确率 > 70%（人工复核） |

## 六、总结：从"采集工程师"到"Agent架构师"的能力跃迁

这个演进路径的本质是：

> **将你在采集侧积累的反爬、稳定性、可观测能力，升级为Agent系统的"感知层"；再在此基础上构建"认知层"（分析）和"行动层"（执行），最终形成完整的GEO智能体闭环。**

你已有的技术资产（NestJS、Kafka、Playwright、Prometheus）都是这个架构的坚实基础，不需要推倒重来，而是**分层叠加**。建议从Phase 1的数据增强开始，小步快跑，每个阶段都有可量化的产出和验证点。
