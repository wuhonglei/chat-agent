# Agent 评估体系实施计划

> 目标：为 chat-agent 项目建立可落地的四维评估体系，从定义标准到工程实现分步推进

---

## 一、四维评估体系

### 维度 1：结果质量——「对不对、全不全」

用户最直接感知的维度，核心两个问题：答案是否正确？该覆盖的信息是否覆盖了？

| 子维度     | 定义                                  | 检查方式                                    |
| ---------- | ------------------------------------- | ------------------------------------------- |
| 准确性     | 回答事实是否与知识源一致，是否产生幻觉  | LLM-Judge 对比标准答案 / 检索上下文          |
| 完整性     | 该回答的信息是否遗漏                   | LLM-Judge 检查要点覆盖率                     |
| 相关性     | 回答是否切题                           | LLM-Judge 判断语义相关性                      |

### 维度 2：过程合规——「有没有越权」

不看答案好不好，看 Agent 执行过程有没有违规。

| 检查项     | 定义                                  | 检查方式            |
| ---------- | ------------------------------------- | ------------------- |
| 工具白名单 | Agent 是否只调用了场景授权的工具       | 规则：集合比对       |
| 权限边界   | 文件操作是否越界（workspace 之外）     | 规则：路径前缀匹配   |
| 调用链合理 | 是否存在无意义重复调用                 | 规则：Trace span 分析|
| 安全合规   | 是否泄露系统 prompt / API key          | 规则：正则扫描       |

### 维度 3：运行效率——「慢不慢、贵不贵」

衡量资源消耗，决定产品能否规模化。

| 指标           | 定义                          | 来源              |
| -------------- | ----------------------------- | ----------------- |
| 端到端延迟     | 用户发消息到收到完整回答       | Trace 时间戳差值  |
| 首 token 延迟  | 流式场景下第一个字的时间       | Trace 首个 span   |
| Token 消耗     | input + output tokens         | Langfuse usage    |
| 工具调用次数   | 一轮对话中的工具调用总数       | Trace tool span   |
| 成本折算       | token × 模型单价               | 计算              |

### 维度 4：结构完整——「答案/证据/编号是否齐全」

检查输出的格式规范性，确保回答可追溯、可解析。

| 检查项     | 定义                          | 检查方式            |
| ---------- | ----------------------------- | ------------------- |
| 结构化格式 | 工具返回是否按约定格式呈现     | 规则：格式校验      |
| 步骤编号   | 多步骤回答是否有清晰编号       | 规则：正则匹配      |
| 必要字段   | 特定场景下的必要信息是否齐全   | 规则：场景化校验    |

## 二、Score Config（评分标准化）

每个指标必须有明确的计算逻辑和阈值，落到 Trace 数据上可执行。

| 指标名               | 分值类型      | 判定逻辑                                | 阈值           | 适用范围     | 优先级 |
| -------------------- | ------------- | --------------------------------------- | -------------- | ------------ | ------ |
| empty_answer         | 布尔          | 回答内容 strip 后长度 == 0              | false = 合格   | 全部         | P0     |
| response_truncated   | 布尔          | finish_reason == "length"               | false = 合格   | 全部         | P2(暂缓) |
| tool_whitelist_ok    | 布尔          | 调用工具集合 ⊆ 场景白名单               | true = 合格    | Agent 模式   | P0     |
| latency_e2e          | 数值（秒）    | Trace 时间戳差值                        | p95 < 8s       | 全部         | P0     |
| input_tokens         | 数值          | Langfuse span 的 usage 字段             | < 8000         | 单轮         | P0     |
| tool_call_count      | 数值          | Trace 中 tool span 计数                 | <= 5           | 单轮         | P0     |
| answer_completeness  | 等级（1-5）   | LLM-Judge 对比标准答案 / 检索内容打分   | >= 3 为及格    | RAG 问答     | P1     |
| answer_correctness   | 等级（1-5）   | LLM-Judge 对比标准答案打分              | >= 3 为及格    | 评估集回归   | P1     |
| user_thumb_down      | 布尔          | 用户点踩                                | false = 合格   | 全部（显式） | P1     |
| user_follow_up       | 布尔          | 30s 内有追问                            | false = 合格   | 全部（隐式） | P1     |
| file_path_boundary   | 布尔          | 文件路径以允许前缀开头                  | true = 合格    | Sandbox 场景 | P1     |
| secret_leak          | 布尔          | 输出不匹配 key/token 正则               | true = 合格    | 全部         | P1     |
| step_numbered        | 布尔          | 多步回答包含编号                        | true = 合格    | 多步骤场景   | P2     |

### 核心原则

1. 每个指标必须可自动计算，落到 Trace 数据上，不靠人工评审启动
2. 分值类型选最简单的够用的——布尔能量化的不要用等级，等级能搞定的不要用浮点
3. 阈值从真实数据定——先跑一遍线上 Trace 看分布，取 p90/p95 做初始阈值
4. 适用范围写清楚——RAG 问答和纯闲聊的指标不同，别一刀切

### empty_answer 与 response_truncated 的区别

两者是互补关系，回答中途被中断不属于 empty_answer：

```
场景                    empty_answer    response_truncated    处理方式
────────────────────────────────────────────────────────────────────────
回答完全为空（""）        true            -                    直接判 0
回答中途被中断（有部分内容） false           true                 送裁判评完整性
回答正常完成              false           false                正常评估
```

**用户主动取消**是最常见的中断场景，但不需要 response_truncated 指标——数据库已有 `MessageStatus.STOPPED` 标记，评估系统直接过滤：

```python
# 只评估正常完成的消息，排除用户取消
messages = [m for m in messages if m.status == "done"]
```

**LLM 截断**（finish_reason == "length"）当前不常见，且 finish_reason 未持久化到 DB，优先级降为 P2。等线上数据证明截断是高频问题后再补充（需先在 chat_session_agent.py 中记录 finish_reason）。

中断原因分类：

```
中断原因                  Trace 里的信号                      处理
────────────────────────────────────────────────────────────────────────
用户主动取消               message.status == "stopped"        评估时直接过滤，不算质量问题
模型触发 max_tokens        finish_reason == "length"(未存储)   P2 暂缓，需补充持久化
服务端异常                 span status == "ERROR"             标记 error，直接判 0
网络中断                   Trace 无收尾 span                  标记 incomplete，人工复核
```

三层逐级深入：先看有没有（empty_answer），再看截没截（response_truncated，暂缓），最后看全不全（answer_completeness）。

## 三、answer_completeness 评估策略

### 评估方式：不强制依赖标准答案

两种思路，分场景使用：

| 策略           | 适用场景            | 是否需要标准答案 | 精度 | 覆盖范围     |
| -------------- | ------------------- | ---------------- | ---- | ------------ |
| 思路 A：对比标准答案 | 评估集回归（门禁）  | 需要             | 高   | 仅评估集内   |
| 思路 B：对比检索内容 | 线上日常监控        | 不需要           | 中   | 全量可评     |

**思路 B 的裁判 Prompt（线上抽样用）：**

```
你是一个回答完整性评估器。

【用户问题】{query}
【检索到的参考内容】{retrieved_contexts}   # 从 Trace 的检索 span 直接取
【模型回答】{answer}

请判断：
1. 参考内容中与问题相关的关键信息点有哪些？（逐条列出）
2. 模型回答覆盖了哪些？遗漏了哪些？
3. 覆盖率 = 已覆盖数 / 总相关要点数
4. 评分 1-5：
   - 5: 覆盖率 >= 90%
   - 4: 覆盖率 >= 70%
   - 3: 覆盖率 >= 50%
   - 2: 覆盖率 < 50%
   - 1: 几乎未利用检索内容

输出 JSON: {"score": int, "coverage": float, "missing_points": [...]}
```

### 分层采样策略

裁判模型不能全量跑（成本高），需要分层采样。

**第一层：规则预筛**

```
规则判定结果          处理方式
─────────────────────────────────
空回答 / 极短回答     直接判 0，不送裁判
纯闲聊 / 单轮寒暄     标记 N/A，不送裁判
有效 RAG / 工具回答    进入裁判候选池
```

**第二层：按风险等级抽样**

```
风险等级    定义                              抽样比例    理由
──────────────────────────────────────────────────────────────────
高风险      涉及工具调用 / 代码执行 / 文件操作    30%-50%    出错代价大
中风险      RAG 检索回答 / 知识库问答             10%-20%    主力场景
低风险      纯模型自由生成 / 通用问答              5%         出错代价小
```

风险等级判定逻辑：

```python
def get_risk_level(trace):
    tool_names = [s.name for s in trace.spans if s.type == "tool"]
    if any(t in HIGH_RISK_TOOLS for t in tool_names):   # execute_code, file_write
        return "high"
    if any(t in MED_RISK_TOOLS for t in tool_names):    # knowledge_search, web_search
        return "medium"
    return "low"
```

**第三层：特殊场景加权**

```
加权场景                         策略           理由
──────────────────────────────────────────────────────────────
用户点踩的                       100% 采样       显式负反馈，必须查原因
追问率高的（30s 内连续追问）      100% 采样       隐式不完整信号
首次出现的新 query 类型          100% 采样       评估集外的新问题
低分历史 query 的变体             100% 采样       bad case 回流
多轮长对话（> 5 轮）              提高到 50%      上下文丢失风险高
```

**完整采样流程：**

```
全部 Trace
  │
  ├─ 规则预筛 ──→ 空回答/闲聊 → 直接打分，不送裁判
  │
  └─ 候选池
       │
       ├─ 特殊场景（点踩/追问/新 query）→ 100% 送裁判
       │
       └─ 常规场景
            ├─ 高风险工具调用 → 抽 30-50%
            ├─ RAG/知识问答   → 抽 10-20%
            └─ 纯生成         → 抽 5%
                                    │
                                    ▼
                              LLM-as-Judge 打分
                                    │
                              ┌─────┴─────┐
                              ▼           ▼
                         >= 3 分       < 3 分
                         及格          进入 bad case 队列
                                      人工复核 + 归因回流
```

**采样量估算（日均 1000 轮有效对话）：**

```
规则预筛后候选池：~600 条
特殊场景加权：~100 条（全采样）
常规抽样：500 条 × 15% ≈ 75 条
─────────────────────────────
裁判模型日调用量：~175 条
```

## 四、运行时机

三种触发时机，各管各的：

| 触发时机            | 评估类型      | 是否阻塞用户 | 执行位置         |
| ------------------- | ------------- | ------------ | ---------------- |
| 每轮问答结束         | 规则评估器    | 同步 < 10ms  | 请求链路内       |
| 用户点踩            | 裁判模型      | 异步不阻塞   | 后台任务队列     |
| 定时批量（凌晨 3 点）| 裁判模型      | 无（离线）    | 独立评估 worker  |

### 规则评估器（实时）

每轮问答结束后同步执行，延迟 < 10ms，写入 Langfuse score。

### 裁判模型（定时批量）

不放在实时链路里，原因：

1. 成本：每轮都调裁判模型，token 费翻倍
2. 延迟：裁判调用 2-5 秒，用户已收到回答，多等无意义
3. 依赖：裁判需要标准答案或检索上下文，实时请求中构造不完整

定时任务（每天 03:00）：

```
拉取过去 24h 的 Trace（规则层已打过基础分的）
  → 过滤候选池（排除已判 0 的空回答）
  → 分层采样（按风险等级 + 特殊信号）
  → 批量调裁判模型（并发控制）
  → 写回 Langfuse score
  → 低分样本进 bad case 队列
```

### 用户点踩（事件驱动）

用户点踩时实时触发，不等定时任务：

```
用户点踩
  → 立即标记该 Trace 为 needs_review
  → 异步调裁判模型（不阻塞用户）
  → 结果 + 点踩原因进 bad case 队列
```

## 五、部署架构

评估逻辑不跑在业务服务器上，也不在 Langfuse 上，而是独立 worker。

```
业务服务器（FastAPI）         独立评估 worker              Langfuse
─────────────────          ─────────────────          ────────────
用户请求进来                 定时触发（cron）             存储 Trace
  ↓                           │                        存储 Score
Agent 处理                     ├─ 拉取过去 24h Trace       ↓
  ↓                           ├─ 分层采样               Dashboard 展示
规则评估器实时跑               ├─ 调裁判模型               趋势/对比/筛选
  ↓                           ├─ 写回 Score
写 Trace + 规则 Score  ──────→│
                              └─ 低分进 bad case 队列
```

Docker Compose 新增服务：

```yaml
evaluator:
  build: ./evaluator
  env_file: .env
  depends_on:
    - backend
  restart: unless-stopped
```

### 为什么不能跑在业务服务器

- 裁判模型调用耗时长，占业务资源，拖慢用户请求
- 裁判调用如果挂了（API 超时、限流），可能影响主服务稳定性
- 扩缩容逻辑不同——业务服务器按并发用户扩，评估 worker 按 Trace 数据量扩

### 为什么不能跑在 Langfuse

Langfuse 是 Trace 存储 + 展示平台，不执行自定义评估逻辑。它能存 Trace、存 Score、提供 API、Dashboard 展示——但不能调裁判模型。

## 六、裁判校准（上线前必做）

裁判模型上线前，用 50-100 条人工精标样本校准：

1. 人工标注 100 条 answer_completeness 分数（1-5）
2. 同一批数据送裁判模型打分
3. 计算一致率（±1 分算一致）：
   - >= 85% → 上线
   - 70%-85% → 调 prompt 重试
   - < 70% → 换裁判模型或拆分评分维度
4. 不一致的 case 单独分析，沉淀为裁判 prompt 的 few-shot 示例

### 思路 B（无标准答案）的波动风险及对策

裁判自己从检索内容提取关键信息点，不同次运行可能提取不一致：

1. 温度设 0（temperature=0），减少随机性
2. 对同一 trace 跑两次取均值，差异 > 2 分的标记存疑
3. 存疑 case 进人工复核队列
4. 有标准答案的评估集定期校准裁判的提取一致性

## 七、实施计划（按优先级排序）

| 步骤 | 动作                                     | 投入  | 产出                              |
| ---- | ---------------------------------------- | ----- | --------------------------------- |
| 1    | 定 Score Config 表（P0 指标 6 个）        | 1 天  | 评估契约文档，后续所有代码围绕它展开 |
| 2    | 从 Langfuse 线上 Trace 采样建评估集       | 2-3 天| 100-200 条标注数据，版本化管理      |
| 3    | 在业务服务器里加规则评估器                | 2-3 天| P0 指标全量跑通，写入 Langfuse     |
| 4    | 规则评估器跑一周，观察数据分布            | 1 周  | 确认阈值是否合理，调整 Score Config |
| 5    | 建独立评估 worker，跑裁判模型             | 3-5 天| answer_completeness 上线           |
| 6    | 裁判校准（50-100 条人工精标）             | 2-3 天| 裁判与人工一致率 >= 85%            |
| 7    | bad case 归因回流流程                     | 1-2 天| 低分样本自动进复核队列              |
| 8    | 评估集接入 CI（改 prompt / 换模型时回归）  | 1 天  | 分数不过不上线                     |

### 第一步具体行动

打开 Langfuse，拉最近一周的 Trace，看线上实际长什么样：

- 有多少空回答
- 工具调用分布（哪些工具被调最多）
- 引用情况（有引用 vs 无引用的比例）
- 延迟分布（p50 / p95 / p99）
- Token 消耗分布

看完数据，Score Config 的阈值才有依据。
