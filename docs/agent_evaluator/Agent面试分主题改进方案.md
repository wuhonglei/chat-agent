# Agent 开发岗面试｜分主题改进方案（完整版）

> 输入：5 家公司 22 个一面/二面卡点 + 简历现状 + 「智能体评估 4 步闭环」框架的缺口修补
> 用法：按优先级从上往下准备；每个主题包含【覆盖问题】【答题框架】【话术要点】【落地动作】

---

## 根因总览

22 个卡点，4 个根因：

1. **「建了什么」讲得清，「做得好不好」讲不清**——效果评估体系缺失（约 1/3 卡点）
2. **「用了什么」讲得清，「为什么是它」讲不清**——选型论证缺对比对象与翻转条件
3. **「怎么集成」讲得清，「内部原理」讲不清**——mem0 等关键组件黑盒化
4. **「正常路径」讲得清，「边界与代价」讲不清**——缺 trade-off 与降级兜底叙事

简历是诱因之一：量化结果全是工程侧指标（延迟、token），没有效果侧指标；「mem0 集成与优化」的措辞给了面试官往下挖的钩子。

## 主题一：Agent 效果评估体系（P0，覆盖 6~7 个卡点）

**覆盖问题**：如何衡量回答准确性 / 如何衡量压缩有效性 / 如何定义产品好坏 / 如何收集与分析 bad case / 如何确保目标不跑偏

### 答题框架：三阶段闭环（对「4 步闭环」的修正版——人工复核不是顺序步骤，是循环内一环）

**① 建设期：先定义什么叫「好」**
- 评分标准化（Score Config）：指标名称、分值类型（布尔/数值/等级）、判定逻辑、阈值、适用范围，全部落到 Trace 数据上，不写口号
- 初版评估集：从线上真实日志采样 100~300 条高频/典型 query，每条含 Input、标准答案、证据来源、场景标签；版本化管理（v1.0 → v1.1）
- 评估维度四类：结果质量（对不对、全不全）、过程合规（有没有越权调工具）、运行效率（慢不慢、贵不贵）、结构完整（答案/证据/编号）

**② 运行期：双轨评估器 + 双通道信号**
- 规则评估器全量跑：工具白名单校验、结构完整性、空回答判 0 分——快、稳、便宜
- 裁判模型（LLM-as-a-Judge）按风险分层**抽样**跑：答案质量、语义合理性——控制成本
- **裁判上线前先校准**：50~100 条人工精标样本算裁判与人工的一致率，达标（85%+）才放行，不一致的 case 反向优化裁判 prompt
- 用户行为信号双通道：显性（点赞/点踩率）+ 隐式（追问率、重试率、会话放弃率）——评估器分数之外，产品好坏最终用户说了算

**③ 迭代期：让闭环真正闭上**
- 低分样本（<0.7）与布尔规则 false 自动进人工复核队列
- 人工归因聚类：检索没召回 / 工具选错 / prompt 歧义 / 模型能力不足 / 上下文丢失，统计分布找最大的桶
- 人工结论回流数据集，沉淀为新标准样本
- **评估集接入 CI**：每次改 prompt、换模型、调架构，跑回归门禁，分数不过不上线——这是「4 步闭环」科普版漏掉的最关键一环

### 专项问题

**「压缩方案是否有效」**：同一评估集跑压缩前后 A/B——任务完成率不降 + token 降幅；再加「关键事实保留测试」：压缩前从长对话抽 N 个事实型 QA 对，压缩后看还能答对几个。

**「执行中目标不跑偏」**：五层手段——system prompt 目标锚定、每轮动态收敛提示、无进展检测（同参数同结果重复即熔断）、step 预算硬上限、复杂任务子目标分解 + 每步校验。

### 落地动作

在现有 Langfuse 基建上补一个轻量版：评估集 100 条 + 规则评估器 3 条 + 裁判校准 1 次 + bad case 回流流程。哪怕规模小，真实发生过就能讲。

## 主题二：记忆系统深度（P0，覆盖 4 个卡点）

**覆盖问题**：mem0 优化体现在哪 / 新旧记忆冲突 / 频繁更新 / 其他开源产品怎么做的

### 核心认知：mem0 的三段式机制（读源码后讲）

naive 做法是「对话全文存向量库、按相似度检索」，mem0 的增量在于记忆是**被维护的**而不是被堆叠的：

1. **提取**：用 LLM 从对话中结构化提取事实与偏好
2. **决策**：新事实与已有记忆比对，LLM 自主判断 ADD / UPDATE / DELETE / NOOP
3. **存储**：向量库存语义记忆；mem0g 引入图结构存实体关系

### 专项问题

- **新旧冲突**：机制上靠决策阶段的 UPDATE 覆盖；工程上叠加时间戳/置信度策略，防止 LLM 误判导致旧事实被错误覆盖
- **频繁更新**：提取放异步队列不阻塞主链路；按会话 debounce 批量提取；同一实体合并写，避免高频写放大
- **横向对比**：Zep（时序知识图谱，强在时序事实）/ Letta·MemGPT（分层内存 + agent 自编辑 memory block）/ LangMem（LangChain 系轻量方案）

### 话术收口

「我用 mem0 但不依赖它——提取-决策-存储三段式我读过源码，冲突合并策略和异步化是我们基于它机制做的增量；选型时对比过 Zep 和 MemGPT，mem0 胜在接入成本和维护活跃度。」

### 延展考点一：短期/长期记忆协同（面试官挖记忆系统的下一层）

**协同架构**：短期记忆 = 会话内上下文（working memory），四级上下文守卫管「容量」；长期记忆 = mem0 持久化，管「跨会话延续」；中间两个阀门——写入阀门（extract 判断哪些事实值得固化）、读取阀门（每轮检索 top-k 相关记忆注入，非全量加载）。

**「3 个月前的偏好还能记住吗」**：能，但关键不在「存没存」在「检不检得出」：
- 召回走语义检索 top-k，当前 query 与该偏好语义相关才注入——「记住」=「相关时能想起来」
- 三个真实风险：① 偏好过时但旧记忆未被 UPDATE；② top-k 漏召回；③ 记忆膨胀后噪声稀释信号
- 治理：recency + frequency 混合评分，久未确认的记忆降权归档——**长期记忆不是永久归档，是带生命周期的工作集**

### 延展考点二：记忆污染场景（四类 + 级联）

| 场景 | 成因 | 后果 |
|------|------|------|
| 幻觉写入 | extract 把推断当事实固化 | 错误前提长期影响回答 |
| 过时信息 | 旧偏好未被 UPDATE，新旧并存 | 检索随机命中，行为不稳定 |
| 冲突记忆 | 多条矛盾记忆同时被召回 | prompt 自相矛盾，输出漂移 |
| 误召回污染 | 低相关记忆相似度虚高被注入 | 带偏当前回答 |
| **级联污染** | 错误记忆作为上下文参与后续提取 | 错误自我强化（反馈回路，加分点） |

### 延展考点三：污染治理（四层结构）

- **写入侧**：置信度阈值，低于阈值进暂存区不直接入库；高风险域（地址/支付/身份）显式确认「我记住了 X，对吗？」
- **存储侧**：版本化——UPDATE 保留历史版本 + 时间戳可回滚；来源标记支持追溯到具体会话
- **读取侧**：矛盾记忆按时间戳/置信度取新降旧；上调相似度阈值防误召回
- **治理侧**：用户记忆管理页（可见可删，顺带覆盖隐私合规）；定期清理任务；**bad case 归因设「错误记忆注入」独立归因桶**——与主题一评估体系联动

### 落地动作

2~3 天读完 mem0 核心源码（extract / update 链路），写一页对比笔记。

## 主题三：技术选型论证（P1，覆盖 3 个卡点）

**覆盖问题**：为什么自研而非 Pydantic AI / Sandbox AIO vs E2B / 联网搜索 vs 直接 API

### 通用框架：决策矩阵四要素

候选清单 → 评估维度 → 各自致命短板 → **翻转条件**（什么情况下我会改选另一个——这句最加分）

### 三个备好的案例

**自研 vs LangGraph / Pydantic AI**
维度：控制粒度、抽象成本、团队熟悉度、生态风险。核心诉求（四级上下文守卫、双层 guardrail）需要 hook 进 ReAct Loop 每一轮，LangGraph 的图抽象对细粒度控制是束缚，Pydantic AI 当时 0.x 早期 API 不稳。自研 loop 核心几百行，控制最全；代价是放弃框架生态，所以工具层坚持 MCP 标准协议补回兼容性。翻转条件：框架的 checkpoint/人机中断能力成熟且我们需要复杂多Agent编排时，会重估。

**Sandbox AIO vs E2B**
维度：隔离级别（容器 vs Firecracker microVM）、启动延迟、资源开销、运维成本、网络管控。AIO 胜在自托管可控、成本低；E2B 胜在隔离强度和冷启动。翻转条件：多租户不可信代码场景上 microVM。

**联网搜索 vs 直接 API**
不是二选一，是互补路由：API 结构化、稳定、便宜，但有覆盖和时效边界；搜索补开放域和时效性。工程做法是先意图分类再路由，结构化需求走 API，开放域走搜索。

## 主题四：效果 vs 成本 trade-off（P1，覆盖 3 个卡点）

**覆盖问题**：Reflection 加不加 / 80% 硬 cutoff 会不会伤效果 / 有没有既省 token 又保效果的方案

### 通用句式

承认代价 → 量化代价边界 → 给出条件触发/分层方案。永远不辩护「我的方案没代价」。

### 三个备好的案例

- **Reflection**：加——自我纠错提质量；代价——延迟与 token 翻倍，且模型自我批评能力有限，可能越改越错。折中：**条件触发**——只在低置信度、工具失败后、高风险操作前插入验证步，而非每轮反思。
- **80% 硬 cutoff**：承认纯按 token 比例截断会在边界误伤（切断半个工具调用块）。改进版：结合语义边界切（在完整工具调用块结束处）+ 超限前提前生成增量摘要，把硬截断变软降级。
- **省 token 又保效果**：分层思想复用——评估侧（规则全量 + 裁判抽样）；上下文侧（四级渐进守卫、短文档全量注入 + 长文档向量检索）；模型侧（简单路由小模型、复杂任务大模型）。一句话：不是单一银弹，是每层各省一点。

## 主题五：稳定性治理——Sandbox（P1，覆盖 2 个卡点）

**覆盖问题**：启动失败降级 / 资源超宿主机限制

- **资源超限**：cgroup 硬配额（CPU/内存/进程数）+ 超时强制回收 + 任务排队限流，超限任务快速失败而非拖垮宿主机
- **启动失败降级链**：预热池兜底 → 指数退避重试 → 最终降级为「无代码执行」的纯文本回答，并明示用户当前能力受限
- 叙事原则：降级不是事故，是设计好的状态机——每一级都有明确的触发条件和用户感知

## 主题六：安全与权限（P2，覆盖 1 个卡点）

**覆盖问题**：Confluence 上每个用户权限不一致，搜索时如何解决（面试官实际关注点）

### 核心答案：身份透传，权限不下沉

- 页面上允许用户配置自己的 Confluence API key
- 检索时以用户身份调用 Confluence API，权限判定由 Confluence 源头执行，返回结果天然在该用户可见范围内
- 我们的系统不复制、不维护权限模型，从机制上杜绝越权

### 设计理由（答题时必讲，拉开差距）

- 权限判定的唯一权威是 Confluence 自己；任何在 RAG 侧重建 ACL 的方案都有两个固有缺陷：**权限同步延迟**（用户刚被移出空间仍能搜到）和**模型不一致**（空间/页面/限制三级权限难以精确复制）
- 零同步成本：权限变更实时生效，无需 webhook 或增量同步；新空间、新页面类型无需适配

### 三个必被追问的兜底

1. **密钥安全**：API key 加密存储（KMS/AES）、不落日志、仅服务端调用；更优解是 OAuth 2.0 on-behalf-of，免用户手动配置
2. **用户不配 key 怎么办**：降级为服务账号只检索全员可见空间，并在结果中提示「配置个人 key 可搜索更多内容」
3. **预索引向量库场景不适用**：内容已离线分块入 pgvector 时，个人 key 帮不上忙——此时用 ACL metadata pre-filter 兜底（同步文档级权限，**检索前过滤**，无权文档不进候选集，而非生成后过滤）。两条路径按检索方式分流：实时工具调用 → 身份透传；离线预索引 → ACL 前置过滤

### 一句话收口

「权限问题上我们的原则是让源头系统当裁判：实时检索走用户个人 API key 身份透传，权限由 Confluence 保证；只有离线预索引的内容，才需要我们在检索层做 ACL 前置过滤兜底。」

## 主题七：可观测性叙事（P2，覆盖 1 个卡点）

## 附录 A：用户凭据安全三层的实现细节（对应主题六追问 1）

### 1. 加密存储

- AES-256-GCM 应用层加密，数据库只存密文；**不要哈希**（key 需解密使用，哈希不可逆）
- 主密钥（32 字节）不进代码库：环境变量 → Docker/K8s Secret → 云 KMS 信封加密，三档递进
- 每次加密随机 nonce；密文格式 `v1.{base64(nonce+ciphertext)}`，版本号前缀支持主密钥轮换后惰性重加密
- 参考实现：`cryptography.hazmat.primitives.ciphers.aead.AESGCM`

### 2. 不落日志

- 兜底：logging.Filter 全局脱敏（正则覆盖 api_key / authorization / token 字段），挂 root + uvicorn logger
- 三个真实泄漏点：① HTTP 客户端异常对象含 request header，catch 后剥离凭据再记；② Langfuse/OTel span attribute 白名单制，凭据不进 trace；③ key 只走 header/POST body，绝不走 URL query（access log 记完整 URL）

### 3. 仅服务端调用

- 前端只进不出：配置页 HTTPS POST 提交一次，接口只回掩码或 `configured: true`
- 明文只在调用 Confluence 瞬间存在于服务端内存，不落盘、不长期缓存
- **Agent 场景关键**：凭据由执行层注入 MCP 工具调用，不进 tool schema / prompt / 工具返回，防止模型把 key 复述进对话与日志
- base_url 白名单：key 只发往配置的 Confluence 域名，防类 SSRF 转发

### 附加项

引导用户创建只读 token；提供轮换/吊销入口；审计日志记「谁在何时访问了哪个空间」，不记 key 本身；单测断言日志输出不含固定假 key（防回归）

## 附录 B：GEO 项目 Agent 化最小改造方案（简历第二 Agent 项目）

### 目的与原则

- 目的：避免 HR 横向对比时只有一个 Agent 项目；优先级低于主题一/二
- 原则：**写进简历的必须真实落地过**；砍掉不会真做的部分（多 Agent 编排、自动发布、RLHF）

### 对原设计方案的三处修正

1. **砍 scope**：4 Agent / 9 个月路线图 → 单 Agent 窄闭环，1~2 周真实落地
2. **重划 Agent 边界**：监控/提取是确定性 DOM 解析 pipeline，**不是 Agent**；Agent 从分析层开始。面试主动讲「确定性环节不强行 Agent 化」= 工具价值论证加分点
3. **删除过度设计**：自动发布（合规风险、不会真做）、RLHF（接不住追问）→ 降级为「基于反馈调 prompt 与策略权重」

### 最小闭环架构

```
现有采集数据 → 指标计算+异常检测（确定性，复用不动）
  → Analyzer Agent（唯一新增 Agent）：ReAct Loop + 4 工具
    （趋势查询 / 信源分布查询 / 竞品对比查询 / 历史案例 RAG）
  → 归因报告（强制带证据引用）
  → 人工审批（人机协作边界）
  → 内容优化 brief 生成（只出建议，不自动发布）
  → 效果追踪（复用现有采样链路）
```

技术实现：Python 独立服务，叙事为「把助手平台验证过的 ReAct Loop 与 guardrail 经验迁移到 GEO 场景」（跨项目能力迁移）。

### 选定的两个难点（均挂回已有面试主题）

1. **证据约束归因（防幻觉）**：每个归因结论强制挂载工具查询返回的数据证据（引用对），无证据不下结论；小评估集人工复核归因准确率 → 挂回主题一评估体系
2. **确定性计算与 LLM 语义层的边界**：趋势/环比/曝光率走 SQL 工具，LLM 只做语义判断与表达 → 挂回主题三选型论证

### 简历定位（与助手平台互补，不撞车）

- 助手平台 = 通用对话式 Agent 平台（引擎/生态/记忆/评估）
- GEO = 垂直业务闭环 Agent（感知层复用采集能力，认知层证据约束归因，人机协作边界）
- 一句话叙事：「第一个项目证明能建通用 Agent 平台，第二个证明能把 Agent 落到具体业务闭环」

## 附录 C：低代码测试平台的 LLM 增强定位方案（第三项目 LLM 叙事）

### 方案定性

级联定位 = 业界 web agent 标准做法（a11y 树文本定位 + Set-of-Mark 标注截图视觉定位），层级按成本递增排列：Similo（确定性）→ a11y 树 + LLM → SoM 截图 + VLM。

### 三个必须讲清的设计点

1. **ref → 定位器的映射**：构建 a11y 树时向 DOM 注入 `data-ebr-ref` 属性，LLM 返回 ref 后直接 `page.locator('[data-ebr-ref="..."]')`，映射活在 DOM 里；不维护外部映射表（DOM 一变就失效）。a11y 树需剪枝：只留可交互/可见元素，过滤 generic 容器，长页面按 viewport 分段
2. **置信度不可信，改闭环验证**：LLM 只出候选（ref + 匹配依据），Similo 对候选再打分做裁判，验证不通过才升级 SoM 截图——与 GEO「证据约束归因」同一设计哲学（LLM 做语义候选、确定性做裁决）
3. **自愈回写**：healed locator 双份回写用例，下次运行直接命中不再付 LLM 成本；自愈结果经人工确认或后续步骤成功后才固化——防止「假通过」（测试场景假通过比失败更危险）

### 阈值与成本叙事

- 85% 阈值来源：历史回放数据统计 Similo 得分分布，取精确率/召回率平衡点
- 各层命中率预期：Similo ~90%，a11y 树解决剩余大部分，SoM 截图仅个位数百分比（图片 token 最贵放最后）
- 汇报指标：级联后定位成功率、LLM 调用率、用例维护工作量下降幅度

### 落地与简历口径

- 项目已结束且已离职 → 至少在自己环境做 PoC（Playwright + VLM，data-ref 注入 + SoM 标注，几百行）
- 简历措辞：「设计并验证 LLM 增强定位方案」；面试可开 demo
- 代码与个人 AI 助手平台的 browser 能力可复用
