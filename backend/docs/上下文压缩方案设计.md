# 上下文压缩方案设计

## 问题分析

当前聊天服务存在上下文超长问题，主要由MCP工具调用返回大量数据导致：

1. **tavily_extract工具**：URL内容提取可能返回200KB+数据
2. **tavily_search工具**：关键词搜索可能返回20KB+数据
3. **上下文累积**：工具调用结果直接传递给响应生成Agent，超出模型上下文窗口限制

## 方案设计

### 阶段1：解决单轮问答上下文超长问题

- 保留关键信息，过滤冗余内容

##### 1.1.2 MCP工具迭代间压缩

**问题分析**：
MCP工具调用支持多次迭代机制，每轮迭代都可能产生大量工具结果。如果不在迭代间进行压缩，会导致：

1. **上下文累积爆炸**：每次迭代的LLM调用都包含所有历史工具结果
2. **性能递减**：后期迭代由于上下文过长导致响应变慢
3. **迭代中断**：可能在达到最大迭代次数前就超出模型上下文限制

**压缩位置**：在`MCPToolsAgent`每次迭代完成后，工具结果生成前

**核心思路**：
- 针对每次迭代的工具结果进行即时压缩
- 维持迭代链路的完整性，避免关键信息丢失
- 平衡当前结果的详细度和历史结果的简洁度

**迭代压缩策略**：
- **当前迭代结果**：保留90%信息（优先保留最新、最相关的结果）
- **最近迭代结果**：保留60-70%信息（2-3轮前的结果）
- **早期迭代结果**：保留30-40%信息或进行激进压缩
- **重复信息过滤**：跨迭代识别并合并相似内容
- **关键路径保留**：确保推理链路的关键节点不被压缩

**压缩触发条件**：
- 总上下文长度超过6000字符时触发
- 单轮工具结果超过2000字符时进行预压缩
- 迭代次数超过3轮时启用历史压缩

### 3.1.1 Agent设计方案

基于现有系统的Agent架构，上下文压缩功能更适合设计为独立的`ContextCompressionAgent`，而不是单纯的服务组件。

#### 为什么选择Agent设计

**上下文压缩方案具有以下Agent特征**：

1. **独立决策能力**：需要根据内容类型、长度阈值等因素智能选择压缩策略
2. **处理复杂逻辑**：涉及多层次的压缩算法（通用压缩、迭代间压缩、历史上下文压缩）
3. **与LLM交互**：可能需要调用LLM进行内容摘要和相关性判断
4. **状态管理**：需要维护会话上下文和压缩历史
5. **流式处理**：可以流式返回压缩结果，支持实时反馈

#### Agent核心架构

```python
class ContextCompressionAgent(BaseAgent):
    """上下文压缩Agent - 负责智能压缩工具调用结果和对话上下文"""

    def __init__(self, think_mode: bool, llm_config: LLMConfig, compression_config: dict):
        super().__init__(think_mode, llm_config)
        self.compression_config = compression_config

        # 压缩器组件
        self.tool_result_compressor = ToolResultCompressor(llm_config)
        self.iteration_compressor = IterationCompressor(llm_config)
        self.conversation_manager = ConversationContextManager(max_rounds=5)
        self.context_monitor = ContextMonitor(llm_config.model_name)

        # 压缩状态
        self.compression_stats = {
            'original_length': 0,
            'compressed_length': 0,
            'compression_ratio': 0.0,
            'processing_time': 0.0
        }
```

#### Agent集成架构


**集成方式**：
1. **工具结果压缩**：`MCPToolsAgent` → `ContextCompressionAgent` → `ResponseGenerationAgent`
2. **迭代上下文压缩**：在`MCPToolsAgent`的迭代循环中调用压缩
3. **会话上下文压缩**：在`ChatService`的多轮对话管理中调用

#### Agent接口设计

```python
async def stream_execute(
    self,
    compression_type: Literal['tool_results', 'iteration', 'conversation'],
    input_data: dict,
    **kwargs
) -> AsyncGenerator[str, None]:
    """
    流式执行上下文压缩

    Args:
        compression_type: 压缩类型
        input_data: 压缩输入数据
            - tool_results: 工具调用结果列表
            - iteration: 迭代上下文数据
            - conversation: 会话历史数据
    """
    if compression_type == 'tool_results':
        async for result in self._compress_tool_results(input_data['results']):
            yield self.format_sse_message('compression_progress', result)

    elif compression_type == 'iteration':
        async for result in self._compress_iteration_context(
            input_data['current_results'],
            input_data['historical_context']
        ):
            yield self.format_sse_message('compression_progress', result)

    elif compression_type == 'conversation':
        async for result in self._compress_conversation_context(
            input_data['history'],
            input_data['current_query']
        ):
            yield self.format_sse_message('compression_progress', result)
```

#### 压缩策略的Agent化实现

**每个压缩器都可以设计为子Agent**：

```python
class ToolResultCompressor(BaseAgent):
    """工具结果压缩子Agent"""

    async def stream_execute(self, tool_results: list) -> AsyncGenerator[CompressedResult, None]:
        # 智能识别内容类型
        content_types = self._analyze_content_types(tool_results)

        # 根据类型选择压缩策略
        for result in tool_results:
            content_type = self._detect_content_type(result)

            if content_type == 'web_content':
                compressed = await self._compress_web_content(result)
            elif content_type == 'search_results':
                compressed = await self._compress_search_results(result)
            else:
                compressed = await self._compress_generic(result)

            yield compressed
```

#### Agent设计优势

**设计为Agent的优势**：

1. **统一架构**：遵循现有的BaseAgent模式，易于集成和维护
2. **智能化**：可以利用LLM能力进行更智能的压缩决策
3. **可扩展性**：新的压缩策略可以作为新的Agent方法添加
4. **可监控性**：继承BaseAgent的token统计和错误处理能力
5. **流式处理**：支持实时压缩进度反馈
6. **配置化**：通过compression_config支持不同的压缩参数

**与服务模式的对比**：
- **Agent模式**：更适合需要决策和LLM调用的复杂压缩逻辑
- **服务模式**：适合纯算法的简单压缩处理

## 风险控制

### 5.1 降级策略
- 压缩失败时使用原始内容（带长度限制）
- 单轮压缩失败时跳过该工具结果
- 多轮压缩失败时只保留最近1轮
- **迭代压缩降级**：
  - 迭代间压缩失败时跳过压缩，继续使用累积上下文
  - 当上下文过长时，优先保留最近2轮迭代结果，丢弃早期结果
  - 极端情况下，终止当前迭代链，返回当前已收集的信息

### 5.2 数据安全
- 敏感信息过滤
- 压缩过程不存储中间结果
- 失败时不暴露原始数据

## 总结

该方案采用**Agent设计模式**，通过分阶段实施，系统性地解决了MCP工具调用结果过长的问题：

1. **阶段1**：解决单轮问答中的上下文超长问题，通过智能压缩单个工具结果，并新增迭代间压缩机制解决多轮工具调用的上下文累积问题
2. **阶段2**：解决多轮对话中的上下文累积问题，通过历史上下文管理和相关性过滤

**Agent设计优势**：
- **架构一致性**：与现有系统的MCPToolsAgent、ResponseGenerationAgent保持统一的Agent架构
- **智能化提升**：充分利用LLM能力进行内容理解和智能压缩决策
- **可扩展性强**：新的压缩策略可以作为新的Agent方法无缝集成
- **监控完善**：继承完整的token统计、错误处理和日志记录能力

方案设计注重实用性，既保证信息保留率，又确保系统稳定性，为后续优化奠定基础。特别针对MCP工具的迭代机制进行了优化，确保复杂推理任务能够顺利完成。
