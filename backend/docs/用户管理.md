# 用户与认证模块说明（当前实现）

> 状态：现网实现。本文档以 `app/api/auth.py`、`app/api/user.py`、`app/core/jwt.py` 为准。

## 1. 认证接口（`/api/auth`）

- `POST /api/auth/sms/send`：发送短信验证码
- `POST /api/auth/sms/login`：短信验证码登录
- `POST /api/auth/wechat/init`：微信登录初始化
- `POST /api/auth/wechat/login`：微信登录回调登录
- `POST /api/auth/logout`：退出登录

说明：

- 登录成功后，服务端会在响应头写入 `x-secret-token-info`；
- 该 token 用于后续业务接口的 `Authorization: Bearer <token>` 鉴权；
- 短信验证码由后端生成并保存在 Redis，验证码有效期为 300 秒。

### 1.1 短信验证码登录约束

`POST /api/auth/sms/send` 成功时返回：

```json
{
  "verification_id": "uuid",
  "expires_in": 300,
  "phone_number": "13800138000"
}
```

关键行为：

- Redis key 格式为 `sms:verify:{verification_id}`，内容包含验证码和手机号；
- 发送短信前先写 Redis，腾讯云短信发送失败时会回滚删除该 key；
- `POST /api/auth/sms/login` 使用 `verification_id` + `verification_code` + `phone_number` 校验；
- 校验成功后删除验证码并按手机号创建或更新用户，JWT 载荷中的 `last_login_type` 为 `sms`；
- 验证码错误或手机号不匹配返回 `400`，验证码保留到 TTL 过期，允许用户重试；
- Redis 读写失败返回 `503`：`验证码服务暂不可用`。

运维检查：

- 应用启动时必须能连通 Redis，否则启动失败；
- `/api/health` 的 `redis` 字段返回 `ok` 或 `unavailable`；
- 本地环境可用 `REDIS__HOST`、`REDIS__PORT`、`REDIS__USERNAME`、`REDIS__PASSWORD` 覆盖 Redis 配置。

## 2. 用户接口（`/api/user`）

- `GET /api/user/detail`：获取当前用户信息
- `PUT /api/user/update_info`：更新用户资料
- `GET /api/user/memories`：分页获取用户记忆列表（见 2.2）
- `GET /api/user/memories/search?q=`：按关键词搜索用户记忆（见 2.2）
- `GET /api/user/memories/{memory_id}`：按 id 查询单条记忆
- `DELETE /api/user/memories/{memory_id}`：删除单条记忆

补充：

- 头像上传：`POST /api/avatars/upload`；读取：`GET /api/avatars/{filename}`。
- 前端记忆管理页：`/memories`（`MemoriesPage` + `DataManage`），从账号菜单进入。

## 2.1 Mem0 用户记忆（聊天链路）

实现：`app/services/user/memory_service.py`，配置根为 `settings.chat_context.memory_config`（`MemoryConfig`）。

启用条件：`base_url` 与 `api_key` **均非空**；否则所有 HTTP 调用直接 no-op / 返回空列表。

请求头同时携带：

- `X-API-Key: {api_key}`
- `Authorization: Token {api_key}`

### 2.1.1 商业版 Platform 与自建 OSS 分流

`MemoryService._is_platform()` 在以下任一条件成立时走 Platform：

- host 为 `api.mem0.ai`（`https://api.mem0.ai` 或 `https://api.mem0.ai/v3` 均可）
- `base_url` 的 path 以 `/v3` 结尾（用于自建但挂了 v3 前缀的网关）

其余地址按自建 OSS 路径调用。Platform 路径**必须带尾斜杠**（Django 否则 301，httpx 默认不跟随 POST 重定向）。

| 能力 | Platform | 自建 OSS | 调用方 |
|------|----------|----------|--------|
| 写入 | `POST {origin}/v3/memories/add/` | `POST {base}/memories` | 对话后处理（fire-and-forget） |
| 搜索 | `POST {origin}/v3/memories/search/` | `POST {base}/search` | `ChatService._search_user_memories`、`GET /api/user/memories/search` |
| 列表 | `POST {origin}/v3/memories/?page=&page_size=`，body `{"filters":...}` | `GET {base}/memories?user_id=&page=&page_size=` | `GET /api/user/memories` |
| 按 id 查询 | `GET {origin}/v1/memories/{id}/` | `GET {base}/memories/{id}` | `GET /api/user/memories/{memory_id}` |
| 删除单条 | `DELETE {origin}/v1/memories/{id}/` | `DELETE {base}/memories/{id}` | `DELETE /api/user/memories/{memory_id}` |
| 删除全部 | `DELETE {origin}/v1/memories/?user_id=` | `DELETE {base}/memories?user_id=` | `MemoryService.delete_all_memories`（现网无对应 HTTP 路由） |

约束：

- 列表已改为**服务端分页**：请求的 `page` / `page_size` 原样传给 Mem0；总数取 envelope `count`，缺省回退为当页条数。不再在应用侧循环拉满 20 页。
- Platform 的 `{origin}` 只取 scheme + host，忽略 `base_url` 上多余 path（`/v3` 不会叠进 URL）。
- 自建 OSS 的 `base_url` **不要**误加 `/v3` 后缀，否则会被判成 Platform 并打商业版路径。
- 写入 body：`messages` + `user_id`（可选 `run_id` / `metadata`）。搜索 body：`query` + `filters` + `top_k` + 可选 `threshold` + 可见性开关（见 2.2）。
- 解析同时兼容裸数组与 `{results:[...]}` envelope。

默认配置（可用 `CHAT_CONTEXT__MEMORY_CONFIG__*` 覆盖）：

| 字段 | 默认 | 说明 |
|------|-----:|------|
| `search_limit` | `5` | 搜索 `top_k` 与本地再截断上限 |
| `search_threshold` | `0.1` | 聊天检索传入 Mem0 的语义分数阈值 |
| `retrieval_decision_enabled` | `true` | 是否启用问答前记忆检索规则闸门；关闭则跳过规则直接 search |

HTTP 超时（写死在 `MemoryService`，非配置项）：

| 调用 | 超时 |
|------|-----:|
| 搜索 | `5s` |
| 写入 / 列表 / 删除 | `30s` |

聊天侧行为：

- **规则闸门**（`retrieval_decision_enabled`，不区分 `agent_mode`）：纯正则、无 LLM。实现见 `app/services/user/memory_retrieval_decision.py`，Langfuse span `memory-retrieval-decision`。判定顺序：
  1. `len(query.strip()) < 5` → 跳过（`reason=short`，如「hi」「好的」）；
  2. 命中 MEMORY 模式 → 检索（`reason=memory`：`我之前` / `上次` / `我的` / `recommend` / `continue` 等）；
  3. 命中 SKIP 模式 → 跳过（`reason=skip`：知识问答、写代码、翻译、计算）；
  4. 都未命中 → 检索（`reason=default`，宁可多查不漏查）。
  SKIP 与 MEMORY 同时命中时走第 2 步，仍检索。单独的「继续」只有 2 字，先被 short 拦下；「please continue」会检索。
- 聊天检索**不传**治理筛选，走 Mem0 默认可见性；管理页筛选见 2.2。
- 搜索结果按 `score` 降序，再按 `search_limit` 截断，映射 `relevance`（≥0.8 高 / ≥0.5 中 / 其余低）后注入 user prompt 的 `<user_memories>`；
- `governance_status` 缺省视为 `active`；**仅非 active** 时写入 `<governance_status>`，避免每条都占 token；
- 命中的记忆会写入用户消息 `message_metadata.user_memories`（供 eval replay 提取）；
- `ChatRequest.memories` 非空时跳过服务端 `memory_search`，直接使用预注入结果；
- `task_action` 为 `continue` / `summarize` 时跳过检索（按钮文案不是新查询，见 `docs/会话管理.md`）；
- 对话结束后由后处理 fire-and-forget 写入 Mem0（user + assistant 两条）；
- Mem0 HTTP 失败只打 warning，不阻断主对话。

产品侧 v1/v2 检索语义与治理方案稿见 `docs/mem0/`（分析 / 规划文档，不等于本仓库 HTTP 契约）。后台 Dream 治理任务**尚未**在本仓库落地；下列治理字段由 Mem0 元数据带回，管理页只读展示。

## 2.2 记忆管理 API 与治理字段

`GET /api/user/memories` 与 `GET /api/user/memories/search` 共用筛选参数；实现：`app/api/user.py`、`MemoryService._build_filters` / `_visibility_flags`。

| 参数 | 列表 | 搜索 | 约束 |
|------|:----:|:----:|------|
| `page` | ✓ | 忽略 | 从 1 开始 |
| `page_size` | ✓ | 忽略 | 1–100，默认 20 |
| `q` | — | 必填 | 1–200 字符 |
| `governance_status` | ✓ | ✓ | `active` / `merged` / `superseded` / `archived` |
| `memory_kind` | ✓ | ✓ | `ordinary`（查询值，排除 `pattern`）或 `pattern` |
| `created_from` / `created_to` | ✓ | ✓ | ISO 8601；`from > to` 返回 `400` |

列表响应：

```json
{
  "memories": [],
  "total": 0,
  "page": 1,
  "page_size": 20
}
```

搜索不走 Mem0 分页：`top_k` 固定 50（`_MANAGEMENT_SEARCH_LIMIT`），响应 `page=1`，`total` / `page_size` 为当次命中条数。前端有关键词时也不做页码翻页，表格 `total` 取当次数组长度。

可见性开关（与 filter 一起发给 Mem0）：

| `governance_status` | 额外 body / query |
|---------------------|-------------------|
| 未传 | 无 |
| `active` | `latest_only=true`（filter 不再写 `governance_status=active`） |
| `merged` / `archived` | `include_merged=true`，并带 `governance_status` |
| `superseded` | 只带 `governance_status=superseded` |

`MemoryListItem` 治理字段（缺省 status 视为 `active`，缺省 kind 为普通记忆）：

| 字段 | 含义 |
|------|------|
| `governance_status` | `active` / `merged` / `superseded` / `archived` |
| `memory_kind` | 仅 `pattern` 表示治理合成；缺省为普通 |
| `synthesized_from` | 合成该条的来源 ID |
| `merged_into` | `merged` 时指向规范记忆 |
| `superseded_by` | `superseded` 时指向新记忆 |
| `governance_pass_id` / `governance_timestamp` / `synthesis_evidence_hash` | 治理 pass 元数据 |

前端 `DataManage`：筛选需回车或点「搜索」才生效（不是输入即搜）；状态 / 类型标签可打开关联记忆弹层（当前页查找，缺失再 `GET /memories/{id}`）：

- `pattern` → `synthesized_from`（来源记忆）
- `superseded` → `superseded_by`（新记忆）
- `merged` → `merged_into`（合并后的记忆）

排障：

- 管理页空白且日志 `Mem0 get_memories failed`：检查 `CHAT_CONTEXT__MEMORY_CONFIG__BASE_URL` / `API_KEY`，以及 OSS 是否误加 `/v3`。
- 列表有数据但搜索为空：搜索走语义 `/search`，不是标题 ILIKE；`q` 太短或 threshold 仅用于聊天检索（管理搜索不传 `threshold`）。
- 筛「生效」仍看到已合并：确认 Mem0 是否实现 `latest_only`；本仓库只转发该开关。

## 3. 鉴权方式

受保护接口通过依赖注入校验 JWT：

- `require_auth`：仅校验认证是否通过；
- `get_auth_token_info`：校验后提取 `user_id` 等载荷字段。

典型流程：

1. 前端调用登录接口；
2. 从响应头读取 `x-secret-token-info` 并持久化；
3. 后续请求携带 `Authorization` 头访问受保护接口；
4. 后端依赖注入完成 token 验证与用户身份提取。
